# RenderGraph 与资源生命周期

> **本章回答**：为什么学渲染时没遇到过的 Pass 和 RenderGraph，到工程阶段突然满屏都是？
> **写作纪律**：正文用自己的语言展开机制与推导，权威定义与完整细节链接主文档锚点，不整篇复制；陌生术语首次出现给出一句话解释。
> **路线位置**：pilot 路线第 4 课（L01 → L02 → L06 → L11 → L13），建议 45 分钟，含动手实验。

## 1. 从一个问题开始

L06 的结尾你已经在特效链里了：一帧要画多遍。先算一笔组织成本的账。假设 5 个 Pass 都要碰同一张中间纹理，最坏情况下两两之间都要排顺序——5×4÷2 = 10 条顺序依赖要人工保证；Pass 数到 8，就是 28 条。每一条漏了是竞态花屏，每一条加多了是 GPU 气泡掉帧——同步错误的典型表现是画面偶尔闪烁或旧帧残留（[显式 API §5.5](../../../04-跨平台与高性能架构/显式API与同步原语.md)）。手写同步的人就在这两个坑之间横跳：**漏 barrier 花屏，多 barrier 卡顿。**

显存这边同样失控：每个 Pass 自己 `createTexture` 一张 8 MB 中间纹理，4 个 Pass 就是 32 MB 长期占用——哪怕它们从头到尾没有同时活在同一时刻。

RenderGraph 要解决的就是这两件事。先把结论说清楚（断言 `E04`）：它是 **CPU 侧的引擎架构**，把 Pass 依赖画成 DAG、编译期自动插同步并复用显存——它管理的是**复杂度与正确性**，不是画质。

## 2. 学习前提

- **L08**：GPU 管线与状态——一个 Pass 内部"画一遍"时发生了什么，见[GPU 与渲染引擎基础与链路 §2.3](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#23-管线与状态)。
- **L10**：barrier 与命令缓冲——同步为什么必须、三类 Barrier 与布局转换，见[显式 API 与同步原语 §3/§5](../../../04-跨平台与高性能架构/显式API与同步原语.md)。
- **L06**：多 Pass 特效链的亲身体验——FBO 离屏渲染串联，见[L06 纹理桥与零拷贝](L06-纹理桥与零拷贝.md)。
- 四个首次出现的术语，先给一句话解释：
  - **Pass**：一次"渲染到某个目标"的绘制阶段。你其实早就见过——L06 的"多 Pass 特效链"里每个 FBO 环节就是一个 Pass，只是当时叫"离屏 FBO"（断言 `E03`）。
  - **DAG**：有向无环图（Directed Acyclic Graph）——箭头有方向、顺着箭头走回不到出发点的图。
  - **barrier**：L10 学过的同步原语，保证"前面的写完成后，后面的读才开始"。
  - **transient 资源**：只在本帧内、几个 Pass 之间存活的中间纹理（对比：场景模型这类跨帧常驻资源）。

## 3. 直观认识

把每个 Pass 想成一个**工人**，每张纹理想成一个**工作台**。工人多了以后，"谁先用工作台、谁用完能收走"必须有人统一安排——不然两个工人同时抢一张台子（数据竞争），或者一台子明明没人用还占着车间（显存浪费）。

RenderGraph 就是**自动排班系统**：工人只申报"我要读哪张台子、我要写哪张台子"，排班表（DAG）由系统画出来，什么时候插"等一下再动手"的牌子（barrier）、哪两张台子可以轮流用同一块地（aliasing），全部由系统在**开工前**（编译期）决定。

> **类比的边界**：排班表不管"活干得好不好"——它不提升任何一次绘制本身的画质与算法效率；它管的是"谁先谁后、场地怎么复用、别打架"。断言 `E04` 把 RenderGraph 定位为 L4 工程架构，解决的是复杂度与正确性问题。另外"排班"发生在每帧循环之外：一次编译、多帧复用（§4.2），不是每帧都重新画一遍排班表。

主文档把这条概念链的层次讲得很清楚（[概念引入说明 §2](../../../00-导航与索引/概念引入说明.md)，断言 `E03`）：

| 概念 | 层次 | 回答的问题 |
|---|---|---|
| FBO / 多 Pass 特效链 | L3 | 一帧怎么画出来（你已经会了） |
| **Pass** | L3→L4 过渡 | 给"一次渲染到目标"起正式名字 |
| RenderPass / Subpass | L4 | 显式 API 里如何**声明与同步**一个阶段 |
| **RenderGraph** | L4 | 多个 Pass 的依赖与资源如何**统一管理** |

## 4. 一步一步理解原理

### 4.1 Pass 的正式名字：从 L3 经验到显式声明

L06 里"绑定 FBO A 画一遍、再绑定 FBO B 画一遍"就是两个 Pass 的原型。到显式 API（Vulkan），这套经验有了正式名字和声明形式：`VkRenderPass` 要求**提前写明**这次用到哪些附件、每个 subpass 读谁写谁（`VkAttachmentDescription` / `VkSubpassDependency`），见[显式 API 与同步原语 §6](../../../04-跨平台与高性能架构/显式API与同步原语.md#6-renderpass-subpass-load-store)。桥梁见[概念引入说明 §Pass/RenderGraph](../../../00-导航与索引/概念引入说明.md#2-pass-rendergraph为什么学渲染时没遇到)。

**关系要说准**：

- **Pass ≈ RenderPass 的"阶段"概念**：两者都指"一次渲染到某个目标的阶段"，这是可以把 L3 经验迁移过来的部分。
- **但 RenderPass ≠ RenderGraph**：`VkRenderPass` 是显式 API 对**单个渲染阶段及其附件/subpass 读写关系**的声明；RenderGraph 是 CPU 侧引擎架构，把**多个 Pass 的依赖画成 DAG**、编译期分配显存、自动插同步（`E04`）。一个是 API 声明单位，一个是工程管理抽象，层级不同。
- **关键差异**：Vulkan 需预先声明附件的 load/store 与 subpass 依赖，OpenGL 绑定 FBO 则由驱动隐式管理同步——不是"同一个东西换名字"，而是"同一类工作从隐式变显式"。

显式声明的回报在移动端格外实在（[显式 API §6.1](../../../04-跨平台与高性能架构/显式API与同步原语.md#6-renderpass-subpass-load-store)，✅）：`loadOp`/`storeOp` 四个选项直接决定 tile memory 的带宽账——中间 Pass 用 `storeOp = DONT_CARE` 让数据留在片上（TBDR 架构），只有最终输出才 `STORE`，这是移动端后处理链最重要的带宽优化之一。这些正是 RenderPass 声明里"提前说清楚"能换来的优化。

### 4.2 RenderGraph 的两大机制：DAG 编译期能算出什么

RenderGraph 把"Pass + 纹理 + 读写关系"抽象成 DAG（[跨平台与高性能架构 §2.1](../../../04-跨平台与高性能架构/跨平台与高性能架构.md#2-rendergraph-架构设计)，✅已验证）：节点是 Pass，边是数据读写依赖——细分的话，"写→读"是消费依赖、"写→写"是顺序依赖（细分口径见 rendergraph-dag 实验的依赖边定义）。声明之后，**编译期**（不是每帧运行时）做两件大事：

**机制一：物理显存复用（Aliasing）**

对每张 transient 纹理，取"首次写入"与"最后一次读取"两个时间点确定它的**生命周期**；生命周期不重叠的纹理，共享同一块物理显存：

```
Pass A 输出纹理 T1（生命周期：Pass 1–3）
Pass B 输出纹理 T2（生命周期：Pass 4–6）
→ 生命周期不相交 → 物理显存复用（Aliasing）
→ VRAM 峰值从 (T1 + T2) 降至 max(T1, T2)
```

（主文档原文用 Frame 1-3/4-6 口径；transient 纹理按本帧内的 Pass 区间表述是同一结构，此处沿用 lab 口径并如实注明。）

主文档给出的实测口径：总显存开销**陡降 40% 以上** **[测试数据-仅供参考]**——这是带标签的参考数据，不是规范承诺，具体收益取决于你的生命周期分布（量化怎么测见 §4.3）。数学化见 §5。

**机制二：自动推导管线屏障（Pipeline Barriers）**

根据 DAG 的读写依赖，编译期自动插入 `vkCmdPipelineBarrier`（Vulkan）等同步原语：保证 Write-Before-Read 顺序、避免过度同步（不必要的屏障会降低 GPU 并行度）、消除人工配置极易引入的死锁与数据竞争。WebGPU 的资源依赖由实现按 usage/transition 隐式处理。一个容易踩的坑（主文档原文警示）：`insertDebugMarker` 只是调试标记，**不是同步原语**——插了它不等于同步了。

编译一次、多帧复用：DAG 不随帧变化时，拓扑排序、barrier 列表、aliasing 方案都是编译期产物，运行期照单执行。

### 4.3 边界：什么时候不值得（objective 3）

RenderGraph 的收益**有前提**（[跨平台与高性能架构 §2.2](../../../04-跨平台与高性能架构/跨平台与高性能架构.md#22-边界-有条件成立)，⚠️有条件成立；断言 `C06` 为 **conditional**，条件：Pass 深度 ≥3 且有分支；单 Pass 不宜）：

**不宜使用**：

- **单 Pass 简单渲染**：DAG 构建与图编译本身是 CPU 耗时；单 Pass 没有依赖可管、没有复用红利，只剩框架开销——过度设计。
- **Pass ≤ 2 且单线结构**：手写双 FBO 环即可，引入图只会带来冗余的 CPU 计算负荷。

**必须使用**：

- **复杂树状混合分支**：多路画面剪辑、实时多层特效、带景深的后期处理管线。
- **特效 Pass 深度 ≥ 3**（工程启发式，**非规范硬阈值**——主文档原文如此）：涉及模糊、描边等空间采样算法时，人工屏障极易出错。
- **多路并发渲染**：避免人工屏障错误引起的致命管线死锁。

收益怎么证明？主文档给出**四维量化**体系（[§2.3](../../../04-跨平台与高性能架构/跨平台与高性能架构.md#23-量化评估维度)，✅已验证）：VRAM Peak（RenderDoc 内存快照对比）、动态显存申请/释放频次（趋近于零）、屏障注入时钟开销（Nsight Graphics Timeline 的气泡时间）、多帧平均 Overdraw——并明确"不能单一靠 FPS"。评测三原则：硬件基准统一（SoC+驱动版本）、输入用例标准化、内核节点物理监控（Systrace/`dumpsys meminfo` 过滤 `gpu_memory`）。

## 5. 数学原理 / 数据形态

DAG 的形式化（实验 formula 字段原文）：

$$
G = (P, E),\;\; \text{barrier} = \text{compile}(G),\;\; \text{peak} = \text{alias}(\text{lifetimes})
$$

节点集 P 是 Pass，边集 E 是依赖——"T 被 Pass i 写、被 Pass j 读"产生一条 i→j 的边；两个 Pass 写同一张 T 产生一条顺序边。执行顺序 = 拓扑排序（lab 的第 3 阶段）。

Aliasing 的峰值公式三件套：

- **符号含义**：纹理 T 的生命周期 `lifetime(T) = [firstWrite(T), lastRead(T)]`；时刻 t 的存活显存 `alive(t) = Σ size(T)，T ∈ 存活集合`。
- **数值算例**：三张 8 MB transient 纹理，生命周期分别为 Pass [1,2]、[2,3]、[3,4]（教学算例）。无复用：8×3 = **24 MB**。错峰图：

```
            Pass1   Pass2   Pass3   Pass4
GBuffer(8M) [███████████]                  生命周期 [1,2]
HDR(8M)             [███████████]          生命周期 [2,3]
Bloom(8M)                   [███████████]  生命周期 [3,4]
峰值同时存活 = 2 张 = 16 MB（Pass2 与 Pass3 时刻）
```

- **工程后果**：`peak` 由"同一时刻存活资源之和"决定，而非"全部资源之和"（lab selfTest 原话）。VRAM Peak 直接决定低端机型能不能开这条特效链；配合 §4.3 的申请/释放频次趋零，运行时不再反复 `vkAllocateMemory`。

对照主文档口径：40%+ **[测试数据-仅供参考]** 是实测参考；上面 24→16 MB（省 33%）是教学算例——两个数字都如实标注来源与口径，不互相冒充。

## 6. 工程应用与常见错误

**一个可复述的排查现场**（由[主文档 §2.2/§2.3](../../../04-跨平台与高性能架构/跨平台与高性能架构.md#2-rendergraph-架构设计)重组的教学案例）：某项目特效链加到第 5 个 Pass 后，低端机型显存超预算、偶发花屏。用 RenderDoc 做内存快照对比：每个 Pass 独立 `createTexture`、无复用，峰值等于全部资源之和；花屏定位为手写 barrier 漏了一条写→读依赖。改造：Pass 声明读写意图 → RenderGraph 编译期接管（拓扑排序 + 自动 barrier + transient aliasing）→ 复测：VRAM Peak 显著下降（主文档同型场景实测口径 40%+，**[测试数据-仅供参考]**）、动态申请/释放频次趋近于零、花屏消失。评测全程遵守三原则（硬件统一、输入标准化、内核节点监控）。

常见误区：

- **"RenderGraph 是 GPU 硬件特性。"** 错。它是 CPU 侧引擎架构（`E04`），GPU 只看到编译期产出的命令与屏障。
- **"上了 RenderGraph 就一定更快。"** 错。单 Pass / Pass≤2 场景更慢（§4.3 边界）；收益要看四维量化，不是 FPS 单指标。
- **"barrier 要人工插满。"** 错。人工只声明读写依赖，barrier 由图编译期自动推导插入（`E04`）。
- **"`insertDebugMarker` 能当同步用。"** 错。它只是调试标记，不是同步原语（主文档原文警示）。
- **"Pass 越多越该上 RenderGraph。"** 不准确。判据是"深度 ≥3 且有分支"这类结构特征（`C06` 条件），不是单纯数量。

## 7. 动手实验

打开 [RenderGraph：依赖、barrier 与显存复用实验](#/lab/rendergraph-dag)（定义在 `tools/labs.json`，离线可运行）。四个任务，每个对应本章一个机制：

1. **关闭 Bloom Pass，观察依赖边、barrier 数量和峰值显存同时下降**——对应 §4.2 机制一/二：少一个节点，边与编译产物同时收缩。
2. **打开 aliasing，对比资源生命周期的错峰与实际占用显存**——对应 §5 的峰值公式（max 而非 sum）。
3. **关闭 Tonemap 后再关 Bloom，看依赖链断裂时下游资源如何消失**——对应"transient 资源"概念：没有消费者的输出会被编译期裁掉。
4. **数一数从手写 barrier 到图编译，哪些工作被挪到了编译期**——对应 §4.2"一次编译、多帧复用"。

做完用实验内置 selfTest 自查：单 Pass 为什么不适合（只剩框架成本）、barrier 谁插入（图编译器）、aliasing 为什么降峰值（峰值=同时存活之和）。实验边界（labs.json note 原文）：资源生命周期按 Pass 区间**近似**，barrier 计数只统计相邻依赖边；真实引擎还要处理队列族转移、布局切换与 acquire/release——数字用于建立直觉而非精确值。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**Pass 多了手写同步两头横跳（§1）→ Pass 本是 L3 老熟人，到显式 API 才有正式声明形式（`E03`，§4.1）→ 把 Pass 依赖画成 DAG，编译期做两件事：自动插 barrier（漏/多的坑都消失）+ transient 显存 aliasing（峰值=max 而非 sum）（`E04`，§4.2/§5）→ 但收益有结构前提：深度 ≥3 且有分支，单 Pass 反而更慢（`C06` conditional，§4.3）→ 收益用四维量化证明，不用 FPS 单指标（§4.3）。**
