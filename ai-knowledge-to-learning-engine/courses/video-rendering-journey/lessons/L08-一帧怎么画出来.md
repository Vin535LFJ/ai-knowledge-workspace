# 一帧怎么画出来

> **本章回答**：一个 draw call 从应用到屏幕，中间经过哪些层？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：主课程 U3 第 2 课（prerequisites：L07），建议 50 分钟。本章无绑定实验（`tools/labs.json` 无 L08 实验），动手形式为帧循环对照走查（§7）。

## 1. 从一个问题开始

把 L07 的带宽账翻过来再看一个现象：你在渲染线程调用了 `eglSwapBuffers()`，函数返回了——**画面却没有出现在屏幕上**。它还要经过系统合成器（SurfaceFlinger）、等 V-Sync（垂直同步——显示器刷新节奏的信号）节奏、再被合成上屏（[面试题库](../../../06-面试知识库/车载渲染引擎/01-OpenGL管线-FBO与离屏渲染.md) 的管线表与 §6、[解码与播放链路 §3.2](../../../02-解码与播放链路/解码与播放链路.md#32-链路-b视频纹理化opengl-渲染详细流程) 的链路表）。"提交"与"显示"之间隔着一整条**异步流水线**。

本章沿一个 draw call 的旅程走完这条流水线：管线有哪些阶段、各管什么（objective ①）；RenderTarget/FBO 怎么支撑多 Pass（objective ②）；CPU 提交与 GPU 执行之间为什么必须排队与同步（objective ③）。

## 2. 学习前提

- **L07**：GPU 的并行结构与带宽账——draw call 的每一步都要在这张账上花。
- **L06**：FBO 离屏渲染与多 Pass 特效链——本章解释它们在管线层的正式身份。
- 四个首次出现的术语，先给一句话解释：
  - **draw call**：应用层向 GPU 提交的一次绘制命令——它触发的不是"画完"，而是"开始排队"。
  - **片元（fragment）**：光栅化产生的"候选像素"——它要经过测试与混合的淘汰赛，幸存者才真正落到帧缓冲。
  - **RenderTarget / FBO**：离屏渲染的输出目标（L06 的特效链就画在它上面）。
  - **Swapchain**：前后台缓冲的交换链——`eglSwapBuffers` 调换的正是它。

## 3. 直观认识

把一帧的绘制想象成**工厂装配线 + 成品仓库**：装配线（GPU 管线）按固定工位顺序加工；成品先放进**仓库**（帧缓冲/Swapchain 后台缓冲），再由**物流**（系统合成器）按发车节奏（V-Sync）送到门店（屏幕）。应用层是**下单方**——它下单（draw call + submit）之后，装配线什么时候开工、成品什么时候上架，都不由它直接控制。

> **类比的边界**：装配线类比不覆盖两件事——第一，"下单"与"开工"之间隔着命令队列与同步原语（§4.3），下单方可以领先工厂 1–3 帧；第二，"物流发车"按 V-Sync 节奏，错过一班就要等下一班（§4.4 的背压）。

## 4. 一步一步理解原理

### 4.1 图形管线：七个工位各管什么（objective ①）

GPU 渲染管线分固定阶段与可编程阶段（[图形与 GPU 工程](../../../03-图形与GPU工程/图形与GPU工程.md)，✅；断言 `V33` 登记阶段流转）：

> 各阶段流转：**顶点输入 → 顶点着色器（坐标变换）→ 图元装配（连点成面、裁剪）→ 光栅化（矢量→片元、插值）→ 片元着色器（上色、纹理采样）→ 测试与混合（淘汰赛、Alpha 混合）→ 输出** ✅

| 阶段 | 类型 | 职责 | 工程注意 |
|---|---|---|---|
| **光栅化** | 固定 | 几何网格 → 离散片元，执行透视修正插值 | 避免超大三角形或极小多边形引起的填充浪费 |
| **片元着色器** | **可编程** | 单个片元的纹理采样、光照计算 | **最大优化焦点**：简化分支、降低采样次数 |

**片元和像素有什么区别？**（checkpoint ①，由上表推导）光栅化把每个被三角形覆盖的屏幕位置都生成一个**片元**——它是"候选像素"；片元还要过测试与混合的"淘汰赛"（深度测试淘汰被遮挡者、Alpha 混合决定叠加方式），**幸存者**才真正写进帧缓冲成为像素。所以片元数 ≥ 像素数——Overdraw（同一像素被重复着色）正是 L07 带宽账里的一行。

### 4.2 RenderTarget/FBO 与多 Pass：给装配线接多个"成品仓"（objective ②）

L06 的特效链之所以能串联，是因为每个 Pass 都画进自己的 **RenderTarget（FBO）**——FBO 是 Pass 的输出目标（[GPU 基础 §2.2](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#2-渲染引擎的核心组成) 资源表：RenderTarget/Framebuffer 的 **load/store action 直接影响带宽**）。多 Pass 与 FBO 的关系一句话：**一个 Pass = 一次"读若干纹理、写一个 RenderTarget"的渲染阶段**；Pass 之间靠"上一个 Pass 的输出纹理作为下一个 Pass 的输入"衔接——L06 的第一道转换 Shader、L11 的 DAG 依赖边，说的都是这条衔接规则。

资源的生命周期要点（§2.2 表原文口径）：Buffer 是否持久映射、RenderTarget 的 load/store、Descriptor 更新频率决定可否复用、PSO（Pipeline State Object——把 shader 与固定功能状态一次性固化的管线状态对象，正式展开在 L10）需要**预热与变体治理**（Shader 变体是"隐形炸弹"——`#define` 组合爆炸导致首次使用卡顿，车机项目要离线编译 + 管线缓存 + 变体裁剪 ✅ §2.3）。

### 4.3 CPU 提交与 GPU 执行：为什么要队列与同步（objective ③）

应用层与 GPU 是**两个异步执行体**（[GPU 基础 §2.4](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#2-渲染引擎的核心组成)，✅）：

- **Fence**：CPU 等 GPU；
- **Semaphore**：队列之间 / swapchain 同步；
- **Barrier**：资源状态转换与内存可见性；
- **Frame in flight**：CPU 可以领先 GPU 1–3 帧，**但必须有上限，否则输入延迟变大** ✅（断言 `V35`）。

为什么必须有队列与上限？如果没有队列，CPU 每提交一个命令就等 GPU 画完——两侧都跑不满（对应主文档 §4.2 验证表第 2 行："GPU 时间轴有气泡 = CPU 提交不足"）；如果不设上限，CPU 无限领先，用户输入对应的画面要等好几帧才出现——输入延迟爆炸。命令的录制与提交走 CommandBuffer（[GPU 基础 §2.1](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#2-渲染引擎的核心组成)：录制 → 提交到图形/计算/传输队列），细节在显式 API 侧展开（[显式 API 与同步原语](../../../04-跨平台与高性能架构/显式API与同步原语.md)，L10 的主题）。

### 4.4 提交 ≠ 显示：eglSwapBuffers 之后还有什么（checkpoint ②）

`eglSwapBuffers` 做的是**提交后台缓冲**（[图形与 GPU 工程](../../../03-图形与GPU工程/图形与GPU工程.md) ✅：双缓冲机制下，收到 V-Sync 信号时把 Back Buffer 与 Front Buffer 调换，避免撕裂）。但"调换"之后画面还要走（[解码与播放链路 §3.2](../../../02-解码与播放链路/解码与播放链路.md#32-链路-b视频纹理化opengl-渲染详细流程) 预览链路原文）：作为 App 控件树里的普通 View 节点，由 **RenderThread** 常规 GPU 混合，打包提交给 **SurfaceFlinger** 上屏——系统合成器按自己的节奏（[面试题库](../../../06-面试知识库/车载渲染引擎/01-OpenGL管线-FBO与离屏渲染.md) 管线表："eglSwapBuffers → 系统合成器 → 显示"，其 §6 有展开）完成最终合成。

断言 `V34` 登记这条"提交 ≠ 显示"的语义。它的阻塞行为也有讲究：`eglSwapBuffers` 的阻塞取决于 swap interval 与队列深度（面试题库原文口径）——**那是 vsync 背压，不是 GPU 计算时间**（排查时的常见误判）。

## 5. 数学原理 / 数据形态

从应用到屏幕的完整层次（源文档 §2.1 链图 ✅ 转载）：

```
场景数据（网格/材质/灯光/相机）
  ↓ 视锥剔除 / 遮挡剔除 / LOD 选择
可见对象列表
  ↓ 按 PSO / 材质 / 纹理排序，减少状态切换（DrawCall 成本：V07）
RenderGraph：Pass 依赖关系 + 资源生命周期
  ↓ 编译：分配显存、决定 aliasing、插入 barrier
CommandBuffer 录制
  ↓ 提交到图形/计算/传输队列
GPU 执行
  ↓ present
系统合成器 → 显示
```

**工程红线**（[GPU 基础 §2.5](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#2-渲染引擎的核心组成)，✅ 原文口径）：不要在渲染线程里做 `glReadPixels`、同步 map、等待文件 IO、等待网络——**任何"等一下"都会变成帧时间尖刺**。这条红线与 L05 §4.4 的 flush 纪律、L02 §4.4 的静默追赶是同一族：**渲染线程里不允许"等"**。

## 6. 工程应用与常见错误

**排查现场**（由源文档 §2.1/§2.5 重组的教学案例）：车机项目偶发"帧时间 P99 尖刺"，GPU 时间轴上却看不到长任务。按本章层次倒推：尖刺不在 GPU 执行段 → 查 CPU 侧提交路径 → 发现渲染线程里有同步 map（等待上传完成）——正是工程红线的第 2 项。修法：改异步上传 + Fence 回调（L10 的同步原语），尖刺消失。层次化排查的顺序：先 GPU 执行段（L07 验证表）→ 再 CPU 提交段（红线四项）→ 再系统合成段（§4.4）。

常见误区：

- **"调了 eglSwapBuffers 画面就在屏幕上了。"** 提交 ≠ 显示：中间还有 RenderThread 合成、SurfaceFlinger（`V34`，§4.4）。
- **"片元就是像素。"** 片元是候选像素，测试与混合会淘汰一部分；Overdraw 计的就是被淘汰的重复着色（§4.1）。
- **"DrawCall 越少一定越快。"** DrawCall 成本与状态切换、绑定、着色器切换共同相关（`V07`）——先确认瓶颈侧（L07 §4.2）再动手。
- **"Frame in flight 开越大越流畅。"** 有上限：无上限时输入延迟变大（`V35`，§4.3）。
- **"等一下没关系。"** 渲染线程里的任何同步等待都是帧时间尖刺（§5 工程红线）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**一个 draw call 的旅程：剔除与排序 → RenderGraph 编译 → CommandBuffer 录制 → 提交队列 → GPU 管线七个工位（`V33`）→ 片元经"淘汰赛"幸存为像素（§4.1）→ 多 Pass 靠 RenderTarget/FBO 衔接，load/store 直接影响带宽（§4.2）→ CPU 与 GPU 异步：Fence/Semaphore/Barrier + Frame in flight 上限（`V35`，§4.3）→ eglSwapBuffers 只是提交，显示要过系统合成器（`V34`，§4.4）→ 渲染线程里不许"等"（§5 红线）。**

再自问三个"为什么"：为什么片元数会大于像素数？为什么 Frame in flight 必须有上限？为什么"提交"与"显示"必须分开理解？
