# 移动端瓶颈与 TBDR

> **本章回答**：为什么桌面端优化经验不能直接照搬到手机和车机？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：主课程 U3 第 3 课（prerequisites：L08），建议 40 分钟。本章无绑定实验（`tools/labs.json` 无 L09 实验），动手形式为 Overdraw 视图走查（§7）。

## 1. 从一个问题开始

桌面端的优化经验，到移动端会三连变形：

1. **"MSAA 随便开"**——在桌面 IMR 上它是带宽换质量；在移动 TBDR 上 resolve 发生在片上，成本反而较低（§4.3 表）——**方向反了**。
2. **"`discard` 少用无妨"**——在桌面它只是关掉 Early-Z；在 TBDR 上还可能打断 HSR/合并流程，导致更多片元被着色（§Q6）。
3. **"依赖上一帧画面很便宜"**——在 TBDR 上需要把整块 tile 从系统内存 `LOAD` 回来，代价高（§4.3 表）。

再算一笔带宽账（[主文档 §3.2](../../../03-图形与GPU工程/光栅化深度与移动GPU架构.md) ✅ 口径，十进制）：720P（1280×720）RGBA8 单次写 ≈ 3.69 MB；读+写 ≈ 7.37 MB；60 FPS ≈ **442 MB/s**。10 个全屏 Pass ≈ **4.4 GB/s**（未计纹理采样与深度）。在 PC 独显上这没什么，在共享 DRAM 的移动 SoC 上（没有 PCIe、CPU/GPU 同一块内存——`E02`），这就是发热与掉帧的全部来源。源文档 §Q1 原文：**移动 SoC 的 DRAM 带宽有限且功耗敏感；TBDR 把片元计算留在 tile memory，就是为了减少系统内存读写**。

## 2. 学习前提

- **L07**：带宽账模板与算术强度——本章是它在移动架构上的落地。
- **L08**：片元与"淘汰赛"——Overdraw 数的就是被重复着色的片元。
- 五个首次出现的术语，先给一句话解释：
  - **IMR**（Immediate Mode Rendering）：桌面 GPU 主流架构——每个三角形立即光栅化、着色、写显存。
  - **TBDR**（Tile-Based Deferred Rendering）：移动 GPU 主流架构——先分块（binning），每块在片上完成着色再一次性写回。
  - **tile memory**：片上存储——TBDR 把中间结果留在片上以免写主存的关键。
  - **Early-Z**：在片元着色**之前**做深度测试，提前剔除被遮挡片元。
  - **MSAA**：多重采样抗锯齿——每像素 N 个覆盖采样点，最后 resolve（平均）回一个像素。

## 3. 直观认识

把屏幕切成一块块**小瓷砖**：TBDR 先把三角形**分派**到它们覆盖的瓷砖上（binning），然后一块瓷砖一块瓷砖地画——所有中间颜色都留在**手里的调色盘**（tile memory）上，整块画完才一次性贴墙（写回系统内存）。桌面 IMR 则是"画一笔就往墙上钉一笔"，中间结果全走显存。

> **类比的边界**：瓷砖类比覆盖"分块与片上完成"，但不覆盖两点——第一，binning 是在**几何阶段**先做的，着色发生在分块之后（顺序与 IMR 不同）；第二，厂商实现差异很大（Mali/Adreno/PowerVR/Apple 各有各的 HSR 与合并策略，§4.5 ⚠️），"每块瓷砖内部怎么画"不能一概而论。

## 4. 一步一步理解原理

### 4.1 TBDR 与 IMR 的核心差异（objective ①）

两种架构的流程（[主文档 §4.1/§4.2](../../../03-图形与GPU工程/光栅化深度与移动GPU架构.md#4-移动-gpu-架构tbdr-vs-imr)，断言 `V36`）：

- **IMR**（桌面主流）：每个三角形**立即**光栅化、着色、写显存；依赖深度缓存与 Early-Z 控制 Overdraw；**带宽压力直接落在显存上**。
- **TBDR**（移动主流：Mali、Adreno、PowerVR 等，实现细节不同 ⚠️）：屏幕切成 tile（常见 16×16 或 32×32）→ 几何阶段先做 **binning**（把三角形分配到覆盖的 tile）→ 每个 tile 的片元在**片上 tile memory** 完成着色与混合 → **一次性写回**系统内存；PowerVR 的 **HSR**（Hidden Surface Removal）在着色前剔除被遮挡片元。

关键差异表（主文档 §4.3，逐行 ✅）：

| 维度 | IMR | TBDR |
|---|---|---|
| 中间结果 | 写显存 | 留在 tile memory |
| 带宽 | 高 | 低（尤其是多 Pass 在 tile 内） |
| `loadOp` | 影响较小 | `LOAD` 代价高（要载入整块） |
| `storeOp` | 影响较小 | `DONT_CARE` 可省写回 |
| MSAA | 带宽换质量 | 片上 resolve，成本较低 |
| `discard` | 关闭 Early-Z | 可能打断 HSR/合并 |
| 依赖上一帧颜色 | 便宜 | 需要 load，代价高 |

这张表就是"桌面经验不能照搬"的清单化版本：**每一条都是方向相反或权重不同的优化建议**。厂商差异（§4.5 ⚠️）再叠一层：Mali 关注 tile 大小与 transaction elimination、Adreno 有 FlexRender 可切换 direct/binning、PowerVR 的 HSR 对不透明友好但 `discard` 影响大、Apple 的 `MTLStoreAction` 语义明确。表中 loadOp/storeOp 是 RenderPass 附件的"载入/写回"动作（显式 API 的正式机制见[显式 API §6.1](../../../04-跨平台与高性能架构/显式API与同步原语.md)，L10 展开）。源文档的面试提醒原文 ⚠️：**不要断言"所有移动 GPU 都是 TBDR"**，应说"主流移动 GPU 采用 TBDR 家族，具体实现与优化建议以厂商文档为准"。

### 4.2 Overdraw 与 Early-Z：一对必须一起理解的概念（objective ②）

**Overdraw 的本质**（[主文档 §3.1](../../../03-图形与GPU工程/光栅化深度与移动GPU架构.md)）：同一像素被多次着色/混合——每次半透明混合都是一次 **Read-Modify-Write**（读 framebuffer 颜色 → 混合 → 写回）。以"单次写"为基准，RMW 是读+写**两次传输**；若再计深度读写，比例还会变化——**源文档只给机制不给倍数**，任何"×N"都要自己按 §3.2 的账实测。

**Early-Z** 是减少它的第一道闸（断言 `V37`，[主文档 §2.4](../../../03-图形与GPU工程/光栅化深度与移动GPU架构.md)）：在片元着色**前**做深度测试，剔除被遮挡片元——被剔掉的片元不再消耗着色与混合带宽。但它有三个失效条件（主文档表格 ✅）：`discard`、写入 `gl_FragDepth`、Alpha Test——因为着色器可能在任何时刻丢弃片元，GPU 无法在着色前判断可见性。补救：Alpha Test 可用 `alphaToCoverage`（用 MSAA 采样覆盖度替代硬 Alpha 截断的折中方案）或预排序减少损失；`discard` 在移动端代价更高（除关闭 Early-Z 外还可能打断 HSR，§Q6）。

配套的两个工具：**Hi-Z**（用深度金字塔做粗粒度剔除，依赖上一帧/预 Pass 深度）与**深度预 Pass**（先只写深度再正常渲染，让后续片元被 Early-Z 剔除——代价是多一次几何提交，**TBDR 上收益取决于实现**，是否值得要用数据验证不默认开启，§Q8）。半透明的配套纪律：**关闭深度写入但保留深度测试**（写深度会让后面的半透明被错误剔除，§Q9）。

### 4.3 MSAA 的成本主要落在哪里（objective ③）

MSAA 的原理与成本（断言 `V38`，[主文档 §5](../../../03-图形与GPU工程/光栅化深度与移动GPU架构.md)）：

- **原理**：每像素 N 个覆盖采样点（2×/4×/8×），几何覆盖按采样点判定；**片元着色通常每像素一次**（除非 sample shading）；**resolve** 把 N 个采样平均为一个像素。
- **成本**：颜色/深度缓冲占用 ×N（或使用压缩）；带宽增加——但 **TBDR 上 resolve 在片上完成，成本较低** ✅。
- **checkpoint ② 的答案**："MSAA 是渲染更高分辨率再缩小吗？"——**不是，那是 SSAA**。MSAA 只在**几何覆盖**层面多采样，每个像素通常仍只着色一次，所以对**着色锯齿**（高光、纹理）无效（§Q5 原文口径）——那需要 SSAA/TAA 或后处理 AA。

选择判据（主文档 §5.3 表）：3D 车模清晰边缘 → MSAA 4×；文字/UI 为主 → 提高分辨率或 MSAA、慎用 FXAA；动态场景性能紧张 → FXAA/SMAA；高端可接受拖影 → TAA。

### 4.4 平台差异的另一个面：连 API 语义都不能照搬

"桌面经验不能照搬"不止发生在硬件架构层，也在 API 层：同一份 WebGPU/WebGL 代码，在不同驱动/后端/任务类型下性能关系不同（断言 `C05`，**conditional**：依赖驱动/后端/任务类型）；而 WebGPU 本身不是 WebGL 的小改版——它更接近现代显式 GPU API（断言 `V09`，已验证）。加上 L06 的 `E02`（移动 SoC 无 PCIe、共享 DRAM），"先说平台、再说结论"是本课程反复强调的表达纪律。

## 5. 数学原理 / 数据形态

带宽账（源文档 §3.2 公式与算例 ✅，公式三件套）：

- **符号含义**：每帧颜色带宽 ≈ Σ(每个 Pass 的读 + 写) × 分辨率 × 4B。
- **数值算例**：720P RGBA8 单次写 ≈ 3.69 MB；读+写 ≈ 7.37 MB；60 FPS ≈ 442 MB/s；10 个全屏 Pass ≈ 4.4 GB/s（未计纹理采样与深度——源文档注明）。
- **工程后果**：源文档原话——这是"**为什么移动端要少 Pass、降分辨率、用 tile memory**"的根本原因。

优化顺序（主文档 §3.3，六条 ✅）：减少 Pass 数量（合并 shader、Kernel Fusion）→ 降低中间纹理分辨率 → 不透明物体从前到后 + Early-Z → 透明物体控制层数 → scissor/stencil 限制绘制区域 → 避免 `discard`。

瓶颈判断实验表（主文档 §6.2，五行 ✅）：降分辨率帧率升=片元/带宽；无变化=顶点/提交/同步；简化 shader 帧率升=ALU；减少采样帧率升=TMU/带宽；关闭混合帧率升=Overdraw/带宽。移动端红线（§6.3）：全屏 Pass 个位数、避免每像素多次 `pow`/`normalize`、避免动态分支发散、半透明层数 2–3 层、中间纹理优先半分辨率。

## 6. 工程应用与常见错误

****排查现场**（由主文档 §6.2/§Q7/§3.3 重组的教学案例）：车机 HMI 半透明图层叠了几层，帧率不稳。用 RenderDoc 的 Overdraw 视图（Q7：Mali Graphics Analyzer/Adreno Profiler/Xcode GPU Capture 同样可用）定位：中央区域 Overdraw 4 层+。A/B 验证：关闭混合（§6.2 第 5 行）帧率上升 → 确认 Overdraw/带宽瓶颈 → 按优化顺序处理（合并 Pass、压半透明层数到 2–3、中间纹理半分辨率），Overdraw 回落、帧率稳定。

常见误区：

- **"桌面优化经验直接照搬。"** IMR 与 TBDR 的优化方向多处相反（§4.3 表逐行）。
- **"MSAA 就是渲染更高分辨率再缩小。"** 那是 SSAA；MSAA 只多采样几何覆盖，对着色锯齿无效（`V38`，§4.3）。
- **"`discard` 随手用。"** 关 Early-Z + 移动端可能打断 HSR；透明占比高时才值得（§Q6）。
- **"深度预 Pass 默认开启。"** 有代价（多一次几何提交），TBDR 收益取决于实现——用数据验证（§Q8）。
- **"所有移动 GPU 都是 TBDR。"** 按源文档 ⚠️ 提醒：说"主流采用 TBDR 家族，以厂商文档为准"（§4.5）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**移动 SoC 共享 DRAM 且带宽功耗敏感（`E02`）→ IMR 的"每三角形立即写显存"在这里代价过高 → TBDR 分块 binning、tile memory 片上完成、一次性写回，外部带宽大降（`V36`）→ Overdraw 的每次半透明混合都是 Read-Modify-Write，Early-Z 是第一道闸，但 discard/写 gl_FragDepth/Alpha Test 会让它失效（`V37`）→ MSAA 的成本在缓冲 ×N 与 resolve，TBDR 上片上 resolve 较低，且它不解决着色锯齿（`V38`）→ 厂商实现差异大，表达先说平台（`C05`/`E02`）→ 优化顺序：少 Pass → 降中间分辨率 → 排序 + Early-Z → 控制层数 → 避免 discard。**

再自问三个"为什么"：为什么 TBDR 上 `LOAD` 代价高而 IMR 无所谓？为什么 `discard` 在移动端是双重代价？为什么 MSAA 对着色锯齿无效？
