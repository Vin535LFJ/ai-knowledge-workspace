# GPU 为什么快

> **本章回答**：TOPS 很高为什么帧率仍上不去？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：主课程 U3 第 1 课（prerequisites：L06），建议 45 分钟。本章无绑定实验（`tools/labs.json` 无 L07 实验），动手形式为带宽账手算（§7）。

## 1. 从一个问题开始

车机 SoC 的宣传页写着几十 TOPS 的算力，可你的渲染帧率就是上不去。为什么？

先把本章最重要的账算出来（源文档 §1.2 ✅）：**1080P RGBA8 一次全屏写 ≈ 8.29 MB（十进制口径，即 7.91 MiB——主文档写作"≈7.9 MB"系二进制口径）；60 FPS 下单次写就是 ≈ 498 MB/s（十进制）**——"一次全屏写"而已。而一个 5 Pass 后处理链（L06 学过的特效链）很容易把外部带宽推到 **GB/s 量级** ✅。带宽按 Pass 累加：特效链每多一个 Pass，这张账就多一行（该口径由本章 §4.2 登记为 `V30`）。

主文档 §4.4 的结论一句话：**"先算带宽，再谈算力。很多'优化 shader'最后不如'少一次全屏 Pass'有效。"** 本章回答三个问题：GPU 的并行结构为什么让"分支"变得昂贵（objective ①）？怎么用带宽与算术强度判断瓶颈在哪一侧（objective ②）？以及为什么把 occupancy（占用率）拉满不是目标本身（objective ③）。

## 2. 学习前提

- **L06**：多 Pass 特效链与 FBO——带宽账的"每个 Pass"单位来自这里。
- 四个首次出现的术语，先给一句话解释：
  - **SIMD**：一条指令同时操作多个数据车道的执行方式。
  - **warp / wavefront**：GPU 调度的最小执行组——组内几十个"车道"（lane）同步执行同一条指令。
  - **occupancy（占用率）**：实际活跃 warp 数 ÷ 理论最大 warp 数。
  - **算术强度**：运算量 ÷ 访存量——比值越高越不容易被带宽卡住。

## 3. 直观认识

把 GPU 的一个 warp 想象成**一排并排的车道**：绿灯亮起，几十辆车（lane）必须执行**同一个动作**。直行时效率拉满；一旦其中几辆车要转弯（分支发散），整排车道只能按"先全体直行、再全体转弯"的顺序串行放行——**浪费的车道就是分支发散的代价**（断言 `V29`）。

> **类比的边界**：车道类比只覆盖"同步执行"这一层。它不覆盖访存——lane 们去仓库（显存）取货的速度才是很多场景的真瓶颈（§4.2）；也不覆盖调度——GPU 会用"换一批 warp 上场"来隐藏取货延迟（§4.3），这是车道图上看不到的。

## 4. 一步一步理解原理

### 4.1 并行模型：分支为什么昂贵（objective ①）

GPU 的并行模型与工程影响（断言 `V29`，[主文档 §1.1](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#1-gpu-硬件基础)）：

| 概念 | 含义 | 工程影响 |
|---|---|---|
| **SIMD** | 一条指令操作多个数据车道 | 向量化好时吞吐高；分支发散时浪费车道 |
| **SIMT** | 单指令多线程（典型如 NVIDIA warp） | 一个 warp 内 lane 走不同分支会**串行化** |
| **warp / wavefront** | 最小执行组（NVIDIA 32 lane、AMD 64 lane **常见**⚠️） | 分支发散、访存合并、寄存器压力都按组分析 |
| thread / invocation | 每个顶点或片元对应的一次着色器执行 | 片元数量通常远大于顶点数量，**填充率常先触顶** |

源文档的关键认知（✅ 原文口径）：**GPU 擅长"很多像素做同一件事"，不擅长"每个像素走不同分支"**——所以移动端/车机 shader 里要谨慎使用动态分支、`discard` 和大循环。这就是 objective ① 的完整答案：分支发散的代价不是"慢一点"，而是**整组车道串行化**——组里只要有一个 lane 走不同分支，其余 lane 的时间就被陪跑掉。

### 4.2 存储层次与带宽账：先算带宽，再谈算力（objective ②）

存储层次自上而下（源文档 §1.2）：寄存器最快容量最小（数量决定 occupancy）→ shared/tile memory 片上低延迟（TBDR 的主战场）→ L1/L2 cache → 显存/系统内存**带宽最贵，跨芯片边界更贵**。

带宽估算模板（[主文档 §4.4](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#4-关键原理速查)，可直接套用）：

```
颜色附件：分辨率 × 通道字节数 × (load + store)
深度附件：分辨率 × 深度字节数 × (load + store)
纹理采样：采样次数 × 分辨率 × texel 字节数
MSAA resolve：样本数 × 分辨率 × 4B
```

断言 `V30` 登记的源口径算例：1080P RGBA8 一次全屏写 ≈ **8.29 MB（十进制）/ 7.91 MiB（二进制，主文档写作 ≈7.9 MB）** → 60 FPS 下 ≈ **498 MB/s（十进制）/ 475 MB/s（主文档二进制口径）**；5 Pass 后处理链 → GB/s 量级 ✅。两个口径各自闭合，不混用（沿用 L01 §1 的 MB/MiB 纪律）。

****算术强度**判断瓶颈侧（源文档 §1.2 原文口径）：`运算量 / 访存量` 越高越不容易被带宽卡住——片元着色器若只是简单混合，通常是**带宽受限**；复杂 PBR/光照则更可能**算力受限**。判据的操作化版本见 §5 的验证实验表（主文档 §4.2）。

### 4.3 延迟隐藏与占用率：为什么拉满不是目标（objective ③）

GPU 靠**切换 warp** 隐藏纹理采样与显存访问延迟（[主文档 §1.3](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#1-gpu-硬件基础)）：一批 warp 去取货时，另一批 warp 继续计算。occupancy = 实际活跃 warp 数 ÷ 理论最大值；提高它的三个手段：减少每线程寄存器、减少 shared memory 占用、控制线程块大小。

但断言 `V31` 登记的边界（源文档 ✅ 原文口径）：**高占用率不是目标本身——如果瓶颈是带宽，增加线程只会更快把带宽打满**。占用率是手段，瓶颈侧（§4.2 的算术强度）才是诊断对象。

### 4.4 别只看 TOPS（objective ③ 的工程延伸）

TOPS 是**峰值算力**，不代表实际帧率（断言 `V32`，[主文档 §1.5](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#1-gpu-硬件基础)）。真实瓶颈常是：带宽、同步等待、DrawCall 提交、Shader 分支发散、Overdraw、显示合成。车机更应看：**P99 帧时间（99% 的帧耗时低于该值——尾部延迟指标）、最坏帧延迟、热稳定性、启动时间**——而不是峰值吞吐。

## 5. 数学原理 / 数据形态

带宽账的一个完整算例（全部数字来自源文档 §1.2 ✅ 口径，公式三件套）：

- **符号含义**：外部带宽 ≈ Σ(每个 Pass 的 load + store) + 纹理采样读 + 顶点读 + MSAA resolve。
- **数值算例**：1080P RGBA8 一次全屏写 = 1920×1080×4B ≈ **8.29 MB**（十进制；7.91 MiB）；60 FPS → ≈ **498 MB/s**（十进制口径；主文档按二进制口径写作 7.9 MB / 475 MB/s）；5 Pass 后处理链 → **GB/s 量级**。
- **工程后果**：少一个全屏 Pass 比优化该 Pass 的 shader 算力更有效（主文档 §4.4 原话口径）；对应主文档 §4.1"少搬数据"——L06 的零拷贝省的是 CPU 侧搬移，L11 的 RenderGraph 里 loadOp/storeOp 优化带宽、aliasing 省的是 VRAM 峰值（另一科目，见 L11 §4.3）。

瓶颈侧的验证实验表（主文档 §4.2 ✅，本章转载）：

| 现象 | 更可能的原因 | 验证实验 |
|---|---|---|
| DrawCall 减半但帧率不变 | GPU 填充/带宽受限 | **降分辨率，看帧率是否明显上升** |
| GPU 时间轴有气泡 | CPU 提交不足 | 看线程栈与 command buffer 录制耗时 |
| 帧时间 P99 尖刺 | 同步等待/编译/分配 | trace 中查 `glReadPixels`、map、alloc、shader compile |
| 温度上来后掉帧 | 功耗/频率限制 | 长时间稳定性测试 + 频率曲线 |

## 6. 工程应用与常见错误

**排查现场**（由主文档 §4.2 表重组的教学案例）：特效链加到 5 个 Pass 后帧率下降，团队先去"优化 shader"——把片元着色器的数学重写了一遍，帧率纹丝不动。用 §4.2 的验证实验：**降分辨率**，帧率明显上升 → 瓶颈是填充/带宽而非算力 → 正确动作是砍全屏 Pass 数量（或降分辨率档位），而不是抠 ALU。这就是"先算带宽，再谈算力"的实操含义。

常见误区：

- **"TOPS 高就快。"** TOPS 是峰值算力，真实瓶颈常在带宽/同步/提交侧（`V32`）。
- **"占用率越高越好。"** 带宽受限时增加线程只会更快打满带宽（`V31`）。
- **"分支写成动态的没关系。"** warp 内发散会串行化整组车道（`V29`）；动态分支、`discard`、大循环都要谨慎。
- **"先优化 shader 算力。"** 先算带宽账（§4.4 模板），很多"优化 shader"不如"少一次全屏 Pass"。
- **"画质拉满再说。"** 画质—帧率—功耗三角（主文档 §4.3）：车机必须定义正常/降级/安全档位，降档顺序建议：后处理 → 分辨率 → 目标数量/LOD → 静态简化图 → 安全岛兜底。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**GPU 以 warp 为组同步执行——组内分支发散整组串行化（`V29`）→ 帧率的第一账是带宽：1080p RGBA8 全屏写 7.9 MB、60FPS 475 MB/s、5 Pass 到 GB/s（`V30`）→ 算术强度区分带宽受限与算力受限，判据是降分辨率实验（§4.2）→ 占用率是隐藏延迟的手段，不是目标——带宽受限时加线程更快打满带宽（`V31`）→ TOPS 是峰值不是帧率，车机看 P99/热稳定（`V32`）→ 优化顺序：先算带宽账，再谈 shader 算力。**

再自问三个"为什么"：为什么分支发散浪费的是整组车道？为什么"少一次全屏 Pass"常常胜过"优化 shader"？为什么占用率拉满反而可能更糟？
