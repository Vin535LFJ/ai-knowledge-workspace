# 纹理桥与零拷贝

> **本章回答**：解码出来的像素帧怎么变成 GPU 能采样的纹理？"零拷贝"真的一个字节都不拷吗？
> **写作纪律**：正文用自己的语言展开机制与推导，权威定义与完整细节链接主文档锚点，不整篇复制；陌生术语首次出现给出一句话解释。
> **路线位置**：pilot 路线第 3 课（L01 → L02 → L06 → L11 → L13），建议 50 分钟，含动手实验。

## 1. 从一个问题开始

接着 L01 的账算。解码器吐出的一帧 1080p YUV420 是 3.11 MB（L01 §5）；特效在 GPU 上做，消费的却是 RGBA——1080p RGBA8888 一帧 8.29 MB（L01 §1）。最朴素的做法：CPU 把 YUV 读出来、在内存里转成 RGBA、再调 `glTexImage2D` 一帧帧上传——每一帧都要 CPU 亲手搬、再过一次总线。

[frame-pipeline 实验](#/lab/frame-pipeline)的 note 里有一笔更扎眼的账：如果走了"GPU 读回 CPU、再上传回 GPU"的弯路，1080p RGBA8888 一帧往返两次就是约 16.6 MB 的**额外** DRAM 带宽，30 fps 即约 498 MB/s——原话是"在移动端足以吃掉一帧预算"。

可手机的 VPU（解码器）和 GPU 本来就坐在同一块芯片上，中间隔着的就是同一块 DRAM。**数据明明就在那里，为什么还要 CPU 搬一遍？** 这就是本章要回答的问题：怎么让像素从解码器直接"流"进 GPU 的采样纹理——以及，这条传说中的"零拷贝"通路，到底省了什么、又**没有**省什么。

## 2. 学习前提

- **L02**：一帧"什么时候显示"已由 PTS 裁定。但 L02 结尾留了个尾巴——"时间正确的像素帧还躺在解码器输出的缓冲里"：PTS 只解决调度，不解决**帧在哪儿**。
- **L01**：YUV 的内存形态（NV12 的 Y 平面 + UV 交错平面）与 stride 概念——本章的转换 Shader 要直接面对这些数据形态。
- **L05 / 主文档 §2**：硬解输出的缓冲所有权——解码器写完的 GraphicBuffer 归谁、怎么移交，数据流向与拷贝成本见[解码与播放链路 §2.2](../../../02-解码与播放链路/解码与播放链路.md)。
- 三个首次出现的术语，先给一句话解释：
  - **OES**：`GL_TEXTURE_EXTERNAL_OES`，OpenGL ES 中专门接收"外部图像"（如视频解码流）的纹理类型；内部格式对 GL 通用采样器不可见（断言 `V04`，已验证）。
  - **SurfaceTexture**：把解码器输出 Surface 的帧"绑定"为 OES 纹理的中间件。
  - **Gralloc / DMA-BUF**：Android 的图形缓冲区分配器及其承载机制——解码器、GPU、合成器共享同一块物理内存的载体。DRAM/DMA/PCIe 三个维度的区分见[概念引入说明 §1](../../../00-导航与索引/概念引入说明.md#1-数据通路dram-dma-pcie-各是什么)（断言 `E01`）。

## 3. 直观认识

把缓冲区想象成**仓库**，把它的句柄（文件描述符）想象成**钥匙**。

- **CPU 搬运路线**：把货从 A 仓库搬进 B 仓库——CPU 逐字节搬，搬的是货本身。
- **共享路线**：解码器、GPU、合成器拿的是**同一间仓库的钥匙**——解码器往里放货，GPU 直接进仓取货。全程没有"搬运"这个动作，只有"钥匙交给下一个人"（缓冲区所有权移交）。

> **类比的边界**：仓库+钥匙不覆盖两件事。第一，"钥匙交接"（BufferQueue 的所有权移交——Android 用这个队列机制在生产者与消费者之间排队传递缓冲区）本身有排队与同步成本，不是免费的；第二，"零拷贝"省的是 **CPU 搬移**，显存内部的格式转换仍然可能发生——解码帧是 YUV，特效链要的是 RGBA，这一步躲不掉（§4.2）。断言 `V05`（已验证）把话说得很准：零拷贝是"**尽量减少拷贝**"，不是绝对 0 拷贝。

[主文档 §3](../../../02-解码与播放链路/解码与播放链路.md#3-视频渲染双链路深度解构surface-直出-vs-opengl-渲染-已验证)（✅已验证）把整条链路分成两条：**链路 A Surface 直出**——解码帧经 BufferQueue 直接投给系统合成器上屏，App 摸不到任何像素（所以也没有特效可言）；**链路 B 视频纹理化**——帧变成 OES 纹理进 OpenGL，特效从这里开始。本章讲的是链路 B：要做特效，就必须先过这座纹理桥。

## 4. 一步一步理解原理

### 4.1 共享缓冲区：updateTexImage 与变换矩阵

链路 B 的前半段（[主文档 §3.2](../../../02-解码与播放链路/解码与播放链路.md#32-链路-b视频纹理化opengl-渲染详细流程)，✅已验证）：

1. MediaCodec 初始化时绑定的 Surface 由 SurfaceTexture 衍生——VPU 解码完成的 YUV 像素直接写进 Gralloc 硬件缓冲（[主文档 §2.2](../../../02-解码与播放链路/解码与播放链路.md#22-数据流向与内存拷贝成本)：Gralloc 缓冲由 DMA-BUF 承载，**CPU 不参与像素搬移**）。
2. `releaseOutputBuffer(idx, true)` 把这一帧投递给 SurfaceTexture，锁存在 GPU 共享显存中，触发 `onFrameAvailable()` 回调。
3. OpenGL 线程调用 **`surfaceTexture.updateTexImage()`**：把最新帧绑定为 OES 外部纹理。注意：这一步交换的是**缓冲区所有权**，不是像素数据。
4. 同时取回 **`SurfaceTexture.getTransformMatrix()`** 给出的纹理坐标变换矩阵——解码输出带相机传感器自带的旋转角度，采样时用这个矩阵把纹理坐标对齐，否则画面方向不对。

用实验的六阶段视角复述一遍（解码器输出 → BufferQueue → SurfaceTexture → OES 纹理采样 → Effect Pass（一轮特效着色器处理）→ 提交显示）：每个阶段只换"**谁持有缓冲**"，不换"数据在哪"。这就是近零拷贝的实质。

断言状态在这里就要如实交代，不能等结尾：

- `C02`"Surface 直出零拷贝"是 **conditional**（成立条件：需绑定 Surface 给解码器）；
- `P02`"全链路零拷贝"目前是 **open / low（contested）**——要成立必须逐平台给出 buffer ownership 与 copy trace，这正是主文档给它标 ⚠️ 的原因。说"全链路零拷贝"之前先自问：每一跳的所有权移交和格式转换都摸清了吗？

### 4.2 OES 为什么不能直接进特效链：第一道转换 Shader

如果 OES 什么都能干，这座桥到 `updateTexImage` 就该结束了。但它有三条硬限制（[主文档 §7.2](../../../02-解码与播放链路/解码与播放链路.md)；内容由 `V04`（verified，Khronos 规范依据）与其成立条件"采样与格式有限制"背书）：

1. **内部格式不可见**：OES 里可能是 YUV 或 RGB 变种，还可能是 tile 格式——`sampler2D` 采样它直接非法，必须显式声明 `samplerExternalOES`，编译器才会生成正确的寻址指令（frame-pipeline 实验 selfTest 原文）。
2. **采样参数受限**：wrap、mipmap 等通用采样配置不能随意使用。
3. **不能跨纹理重复采样、无法直接回读**：美颜、LUT 调色这类要"反复读周围像素"的特效根本没法做。

工业界的标准解法（[主文档 §7.4：工业级特效管线](../../../02-解码与播放链路/解码与播放链路.md#74-工业级特效滤镜核心管线oes-fbo-2d纹理-已验证)，✅已验证）：**FBO（Framebuffer Object，帧缓冲对象——把渲染结果画进一张离屏纹理而非直接上屏）离屏渲染 + 第一道转换 Shader**。

```
[MediaCodec 硬解]
      │   VPU 直写 Gralloc，CPU 不搬像素
      ▼
[SurfaceTexture] → 绑定为 OES 外部纹理
      │
      ▼   第一道转换 Shader：变换矩阵 + YUV→RGB
[FBO 离屏渲染] → 标准的 GL_TEXTURE_2D（RGBA）
      │
      ▼
[特效链] ─→ 预览：TextureView 上屏
         └→ 导出：编码器 Input Surface 硬编
```

第一道转换 Shader 干两件事，恰好把 OES 的两大"外来属性"洗掉：

```c
// 教学骨架：第一道转换 Shader 的片元着色器（GLSL ES，非完整可运行代码）
#extension GL_OES_EGL_image_external : require
uniform samplerExternalOES uTex;   // 采样 OES 只能用它；sampler2D 是非法的
uniform mat4 uTexMatrix;           // getTransformMatrix() 的结果
varying vec2 vTexCoord;
void main() {
    vec2 uv = (uTexMatrix * vec4(vTexCoord, 0.0, 1.0)).xy; // 矫正旋转/裁剪
    // YUV→RGB 矩阵运算在此展开（示意；系数与 range 约定见 L03/色彩管理）
    gl_FragColor = yuv2rgb(texture2D(uTex, uv));
}
```

YUV→RGB 这一步把 L01 的数据形态换算成特效链要的 RGBA——矩阵系数与 range 约定的完整机制在[色彩管理与采样滤波](../../../03-图形与GPU工程/色彩管理与采样滤波.md)（pilot 路线 L03 专门展开）。关键定位：这次转换发生在**显存内部**——[主文档 §7.3](../../../02-解码与播放链路/解码与播放链路.md#73-零拷贝的真实含义-有条件成立) 说纹理化路径是"显存内一次格式转换，**接近**零拷贝"，这正是 `V05`"尽量减少"而非"绝对 0"的实例。

过桥后的标准 2D 纹理分两路（[主文档 §8.3 对比表](../../../02-解码与播放链路/解码与播放链路.md#83-预览与导出生成双链路闭环架构对比表-已验证)，✅已验证）：预览渲染到 TextureView 上屏，导出渲染到编码器 Input Surface 硬编；两条管线**共享同一套特效 Shader** 以保证所见即所得。注意：这是 Shader 代码复用，不是共享 RenderGraph——RenderGraph 是 L11 的工程架构议题。

### 4.3 两种平台的通路差异：为什么手机"天然"适合零拷贝

先唤起 L01 埋下的三个词：DRAM 是存储介质（数据住哪）、DMA 是传输机制（谁搬）、PCIe 是物理总线（走哪条路）——三个不同维度，不是同一样东西的三个叫法（[概念引入说明 §1](../../../00-导航与索引/概念引入说明.md#1-数据通路dram-dma-pcie-各是什么)，断言 `E01`）。落到"解码帧进 GPU"这件事上，两个平台的形态完全不同（断言 `E02`，已验证；**成立条件：平台与驱动有差异，表述先说平台**）：

| | PC + 独立显卡 | 移动 SoC |
|---|---|---|
| GPU 的数据在哪 | 独立显存 | 与 CPU 共享同一块 DRAM |
| 跨芯片搬移 | 系统内存 → 显存要跨 PCIe、由 DMA 搬移 | 不存在这一步（没有 PCIe 这条"路"） |
| "零拷贝"的含义 | 减少跨总线搬移的次数 | 缓冲共享，CPU/GPU 同址访问 |
| 典型解码输出路径 | 主存 →（PCIe + DMA）→ 显存 | VPU → Gralloc（DMA-BUF）→ GPU 直接采样 |

推论：移动 SoC 没有那条"路"，也没有"两个仓库"——CPU 和 GPU 面对的是同一块 DRAM。零拷贝在移动端价值最大，因为省掉的是**本来就不必要**的搬移；而 PC 独显上谈"零拷贝"要谨慎：数据从主存到显存总归要跨一次总线，能讨论的只是"谁搬、搬几次"。

## 5. 数学原理 / 数据形态

把两条路径的"每帧搬运账"并排放（1080p；MB 为十进制，口径沿用 L01）：

```
软解 / CPU 拷回路径（每帧）：
  码流 → 主存 → CPU 解码 → 主存 →（glTexImage2D 总线拷贝）→ 显存
  CPU 经手像素：是；额外搬移 ≥ 2 次

硬解共享路径（每帧）：
  码流 → VPU → Gralloc 缓冲（DMA-BUF）→ GPU 采样
  CPU 经手像素：否
```

公式三件套（对应实验里的拷贝路径对比）：

- **符号含义**：每帧额外带宽 = 单帧 RGBA 字节数 × 额外拷贝次数。
- **数值算例**：1080p RGBA8888 单帧 8.29 MB（L01 §5）；"读回 + 再上传"= 2 次拷贝 → 16.6 MB/帧；30 fps → 约 498 MB/s 的**额外** DRAM 带宽。
- **工程后果**：实验 note 原文——"在移动端足以吃掉一帧预算"。这也是主文档 §2.2 把"回读 ByteBuffer 再上传"明确排除出零拷贝（⚠️有条件成立）的量化原因。

对比硬解共享路径：同样一帧 3.11 MB 的 YUV420（L01 §5），从 VPU 到 GPU 采样 CPU 搬移 0 次，显存内仅剩 OES→2D 的一次格式转换（§4.2）。省的是 CPU 搬移与总线往返，不是"什么都没发生"。

## 6. 工程应用与常见错误

**一个可复述的排查现场**（由[主文档 §2.2/§2.3](../../../02-解码与播放链路/解码与播放链路.md#22-数据流向与内存拷贝成本)重组的教学案例）：某团队接手一个"明明用了硬解，却发热掉帧"的项目。查链路发现：解码器配置的是 ByteBuffer 输出——CPU 把每帧读回主存、再 `glTexImage2D` 上传。按 §5 的账倒推：CPU 每帧要经手 3.11 MB 的 YUV 读回，转出 8.29 MB 的 RGBA 再总线拷贝给 GPU——30 fps 就是每秒 340 MB 上下的数据过 CPU 之手（还含一次格式转换），发热与掉帧都指向这里。修法：初始化 MediaCodec 时改绑 SurfaceTexture 衍生的 Surface（这正是 `C02` 的成立条件），让 VPU 直写 Gralloc、GPU 直接采样 OES——CPU 搬移归零，只剩显存内一次 YUV→RGB。一个"绑没绑 Surface"的开关，决定整条链路的性质。

常见误区：

- **"零拷贝 = 零成本。"** 错。`V05` 的条件写明：驱动或格式转换仍可能触发拷贝；纹理化路径至少有显存内一次 YUV→RGB（§4.2）。
- **"Surface 直出一定零拷贝。"** 不完整。`C02` 是 conditional：前提是绑定 Surface 给解码器；没绑就落到 ByteBuffer 回读路径（§6 排查现场）。
- **"全链路零拷贝，照抄就完了。"** `P02` 是 **open/low（contested）**：需要逐平台给出 buffer ownership 与 copy trace 才能成立（B11 已确认 L06 保留挂载，升级要等逐平台证据）。
- **"OES 纹理用 sampler2D 也能采。"** 错。必须显式声明 `samplerExternalOES`（frame-pipeline 实验 selfTest），否则编译不过。
- **"手机 SoC 也走 PCIe 传纹理。"** 错。移动 SoC 无 PCIe，CPU/GPU 共享 DRAM（`E02`）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**CPU 逐帧搬像素要付约 16.6 MB/帧的额外带宽（§5）→ 所以让解码器 DMA 直写 Gralloc，缓冲区所有权沿 BufferQueue 移交（`E01`/`E02`）→ `updateTexImage` 把最新帧绑成 OES 纹理、`getTransformMatrix` 矫正方向（`V04`，§4.1）→ OES 三条限制：格式不可见、采样受限、不可回读 → 第一道转换 Shader 经 FBO 把它洗成标准 2D 纹理（§7.4，§4.2）→ 特效链之后预览/导出共享同一套 Shader（§8.3）→ 零拷贝是"尽量减少"而非"绝对 0"（`V05`），全链路零拷贝仍是 open 断言（`P02`）。**

再自问三个"为什么"：为什么特效链必须先过 FBO，而不能直接消费 OES？为什么移动 SoC 上的零拷贝比 PC 独显上更"彻底"？为什么 `P02` 现在还不能当结论引用？

本章解决了"**帧在哪儿**"：L02 留下的那批时间正确的像素帧，现在经共享缓冲区进了 GPU，并被第一道转换 Shader 洗成特效链能消费的标准 2D 纹理。但当一帧要画多遍——阴影一遍、主场景一遍、后处理再来一遍——"谁写哪张纹理、谁读哪张、用完何时释放"就成了新的失控点；靠人肉记顺序的渲染代码，规模一大必然出错。[下一章](L11-RenderGraph与资源生命周期.md)讲 RenderGraph 如何把它变成可管理的工程问题。
