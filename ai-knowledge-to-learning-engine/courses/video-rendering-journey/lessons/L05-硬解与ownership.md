# 硬解与 ownership

> **本章回答**：为什么硬解路径里线程 ownership 比 API 调用更重要？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释；无直接出处的内容明确标注为推导。
> **路线位置**：主课程 U2 第 2 课（prerequisites：L04），建议 40 分钟。本章无绑定实验（`tools/labs.json` 无 L05 实验），动手形式为回退状态机走查（§7）。

## 1. 从一个问题开始

两句话都常听，但都埋着坑：

- **"硬解一定更快更省电。"** 源文档的功耗行原文写着：**"具体比例依 SoC 与码流而定，不能泛化为固定 10%"⚠️有条件成立**——而且低端机 VPU 实例有限，**多路并发时硬解可能反而不如软解灵活**（断言 `C03` 是 conditional，条件：看设备/码率/分辨率/驱动）。
- **"不想要这帧就 flush 掉重解。"** 解码器的输出 buffer 是**有限池**：L06 实验 task 4 让你"把队列深度调到 1，理解为什么在途帧太少会导致解码器等待"——buffer 拿在手里不还，解码器就停摆。谁持有、谁归还、什么时候能销毁，这就是 **ownership（所有权）** 问题。

本章回答三件事：buffer 怎么流转（objective ①）、硬解的功耗优势到底成立于什么条件（objective ②）、什么时候以及怎么安全地回退软解（objective ③）。

## 2. 学习前提

- **L04**：MediaCodec 的定位——仅负责编解码计算、不感知容器（断言 `V01`）；封装流与码流的区别。
- **L02**：精准 seek 的"静默解码追赶"——本章回退状态机的第 7 步就是它。
- **L06 预告**：GraphicBuffer 经 BufferQueue 移交所有权、SurfaceTexture 绑定 OES——本章把"移交"讲清楚，L06 讲"移交之后怎么共享"。
- 三个首次出现的术语，先给一句话解释：
  - **VPU**：SoC 内的专用视频处理单元（ASIC），硬件解码的物理执行者。
  - **buffer 流转**：MediaCodec 的输入/输出缓冲在"应用层 ↔ 解码器"之间的借用与归还循环。
  - **Fallback 状态机**：硬解崩溃或不可用时，无感切换到软解的一套固定步骤（源文档 §8.4，✅）。

## 3. 直观认识

继续用 L06 的**仓库+钥匙**类比：解码器的 buffer 是一排**数量有限的周转箱**——VPU 把货装进箱子，应用层凭 `dequeue` 借走、用完凭 `release` 归还。钥匙总数有限：**拿在手里不还，流水线就等**；**箱子没空就硬塞，VPU 就停**。

> **类比的边界**：周转箱类比不覆盖两件事。第一，"还箱子"有两种还法——`render=true` 把箱子连同货一起交给显示队列（所有权移交给消费者），`render=false` 是空箱直接退还（L02 静默追赶丢帧用的就是这种）；第二，硬解崩溃时箱子可能整体作废，需要整套换软解的箱子——那就是回退状态机（§4.3）。而"省电"来自 VPU 是专用电路（§4.2），与箱子怎么流转无关。

## 4. 一步一步理解原理

### 4.1 MediaCodec 的 buffer 流转（objective ①）

输入侧与输出侧各有一个循环（步骤见[解码与播放链路 §3.1](../../../02-解码与播放链路/解码与播放链路.md)，断言 `V27` 为本节流转规则的登记条目）：

```
输入侧：dequeueInputBuffer() 借空箱 → 填入码流 → queueInputBuffer() 交回解码器
输出侧：解码完成 → dequeueOutputBuffer 取得结果
        → releaseOutputBuffer(idx, render=true)   交给渲染（BufferQueue → Surface）
        └ releaseOutputBuffer(idx, render=false)  直接归还（丢帧，L02 静默追赶语义）
```

- 输入侧：应用层调用 `mediaCodec.dequeueInputBuffer()` 获取空闲缓冲，`queueInputBuffer()` 将 NALU 压入解码队列（主文档 §3.1 第 3 步 ✅）——**借与还必须成对**。
- 输出侧：`releaseOutputBuffer(index, render=true)` 时，像素经 BufferQueue 投递给下游（§3.1 第 5 步 ✅）；`render=false` 则不渲染、buffer 归还——L02 的静默追赶正是"解出的 B/P 帧全部 `releaseOutputBuffer(index, false)` 丢弃"（[主文档 §8.2](../../../02-解码与播放链路/解码与播放链路.md)）。
- ownership 规则（本节推导 + L06 实验佐证）：**buffer 的所有权在"解码器 ↔ 消费者"之间移交，任何一方持有超时都会让有限池耗尽**——L06 实验 task 4（队列深度调到 1，解码器等待）就是这个规则的可视化。

### 4.2 硬解为什么省电，但不是绝对更快（objective ②）

物理原因（[主文档 §2.1](../../../02-解码与播放链路/解码与播放链路.md#2-软解与硬解深度对比-已验证)）：硬解依赖 SoC 内固化的 **VPU 专用电路**，"硬件电路自驱完成硬解码，几乎不消耗 CPU 算力核心"；软解是 CPU 上跑数学算法（NEON/AVX2），"极度依赖 CPU 的多核算力及向量指令集"。

但优势带四个条件（断言 `C03` **conditional**，条件：看设备/码率/分辨率/驱动；[主文档 §2.4](../../../02-解码与播放链路/解码与播放链路.md#2-软解与硬解深度对比-已验证) ⚠️有条件成立）：

| 维度 | 翻车点（源文档原文口径） |
|---|---|
| 设备差异 | 低端 SoC 的 VPU 实例有限，**多路并发时硬解可能反而不如软解灵活** |
| 码率与分辨率 | 低分辨率下软解 CPU 开销可接受，硬解初始化开销可能抵消收益 |
| 驱动实现 | 部分厂商硬解驱动 Bug 会导致性能回退 |
| 编码格式 | 硬解对格式支持有限，不支持的只能软解 |

多维度对照表（§2.3 ✅）还给出两条本章要用的硬信息：**显存传输成本**——MediaCodec 走 Gralloc/BufferQueue 共享（零拷贝前提是绑 Surface，§2.3 表注原文）；**非标码流鲁棒性**——软解"极强（可改源码容错）"、硬解"极差（非标 GOP/Profile 极易黑屏/挂起）"。功耗行原文：**"具体比例依 SoC 与码流而定，不能泛化为固定 10%"** ⚠️——所以任何"硬解省电 X%"的绝对数字都要先问口径。

正确表述（§2.4 原文口径）：**在硬件支持的前提下，硬解通常在功耗、延迟和帧率稳定性上优于软解；但"一定更快"需附加设备、码率、分辨率、驱动和实现路径等条件限定。**

### 4.3 回退软解：触发条件与八步状态机（objective ③）

什么时候必须回退（[主文档 §8.4](../../../02-解码与播放链路/解码与播放链路.md#8-播放器与剪辑架构设计)，✅）：视频流**分辨率突变**、硬解抛出不可恢复异常（`CodecException`）、**硬解实例耗尽**、驱动崩溃、网络丢包导致 GOP 严重不完整、非标 Profile/格式不受支持（§2.3/§2.4）。断言 `V28` 登记这套状态机。

八步无感回退（源文档 §8.4 原步骤，✅）：

1. **拦截硬解错误**：精准捕获 `CodecException`；
2. **画面挂起拦截**：锁存崩溃时刻的黄金进度 `PTS_fail`，渲染器切入"冻结最后一帧"，物理隔绝黑屏/白闪；
3. **音频静音渐变**：包络平滑 Fade Out，阻断瞬间爆音；
4. **销毁硬解上下文**：优雅释放崩溃的解码器实例与关联 Surface；
5. **初始化软解器**：毫秒级初始化 `libavcodec`；
6. **Seek 至安全点**：定位到 `PTS_fail` 之前最近的 I 帧；
7. **静默追赶**：软解全负荷"解出不渲染"，直到 PTS 追平 `PTS_fail`（L02 的机制在这里复用）；
8. **恢复渲染**：视频恢复 + 音频 Fade In，用户无感。

注意状态的**顺序**不能换：先冻结画面再销毁、先渐隐再切音轨、先 seek 再追赶——每一步都在保护上一条因果链（§4.4 会展开为什么顺序错不得）。

### 4.4 RenderThread 为什么不应直接 flush codec（checkpoint ②，推导 + 如实标注）

**先如实声明**：源文档没有"flush codec"专节——本节由 §8.4 状态机的步骤设计与 §4.1 的 buffer 所有权规则**推导**，推导结论已按候选登记于[验真队列与术语表 ❗ 表 P07](../../../00-导航与索引/验真队列与术语表.md)（缺官方文档核验与实测复现，未登记为断言）。

由已验证事实推导：§8.4 的八步里，**销毁/重建解码器被安排在第 4–5 步，且前面必须先做 1–3 步**（锁存 `PTS_fail` → 冻结最后一帧 → 音频渐隐）。为什么不能跳过前三步直接 flush/销毁？

- 直接 flush 会把**在途 buffer 的所有权链**当场打断（§4.1：借出未还的输入缓冲、已投递未消费的输出缓冲一起被收回）——正是 L06 实验 task 4 里"队列深度/在途帧"纪律要保护的东西；
- 没有"冻结最后一帧"先行，销毁期间渲染端无帧可画——黑屏/白闪（§8.4 第 2 步的存在目的，✅ 原文"物理隔绝黑屏或白闪"）；
- 没有音频渐隐先行，切解码器瞬间的爆音无法阻断（§8.4 第 3 步，✅）。

**推导结论**（待核验）：codec 的 flush/销毁/重建属于 **codec 线程或播放器控制流的状态机动作**，RenderThread 只消费渲染结果——把 flush 从渲染线程随手发起，等于绕过状态机的保护顺序。这条推导与源文档 §8.4 的工程结构一致，但"RenderThread 直接 flush 会导致 X"的精确故障表述需实测/官方文档核验后方可升级断言。

## 5. 数学原理 / 数据形态

**buffer 生命周期循环**（ASCII；对应 §4.1）：

```
        ┌────────────── 应用层 ──────────────┐
输入：  dequeue(借) ──> 填码流 ──> queue(还)
输出：  codec 完成 ──> release(true)=交显示队列（所有权移交）
                     └─ release(false)=直接归还（丢帧）
约束：  池容量有限 → 借出未还 = 解码器等待（L06 实验 task 4）
```

**软硬解搬运账**（anchor [主文档 §2.2](../../../02-解码与播放链路/解码与播放链路.md#2-软解与硬解深度对比-已验证)）：软解路径每帧多**一次**"主存 → 显存"总线拷贝（源 §2.2 路径原文）；若走 ByteBuffer 读回弯路才是"往返两次"的账（主文档 ⚠️ 口径 + L06 实验注意）——两种口径不可混用。硬解共享路径 VPU 直写 Gralloc、CPU 零搬移——这是"省电"的物理基础，也是 §4.2 条件限定的边界（跨 PCIe 的平台另算）。

**回退代价**（由 §8.4 推导）：切换期间画面冻结在 `PTS_fail`、音频静音，恢复延迟 ≈ 静默追赶需要解完的帧数 ÷ 软解速度——帧数越多代价越大，所以第 6 步"Seek 至安全点"把追赶起点拉回最近 I 帧，是对代价的主动压缩。

## 6. 工程应用与常见错误

**排查现场**（由源文档 §2.3/§8.4 重组的教学案例）：车载多路播放器在低端 SoC 上"第三路视频黑屏后崩溃"。倒推：多路并发 → VPU 实例耗尽（§2.3 多路并发行）→ MediaCodec 抛 `CodecException` → 若无 §8.4 状态机，直接黑屏；有状态机则按八步无感切换软解（第三路的分辨率低，软解 CPU 开销可接受——§2.4"码率与分辨率"因素）。复盘要点：**回退不是失败，是设计的一部分**；没设计状态机的播放器，等于把"实例耗尽"直接暴露给用户。

常见误区：

- **"硬解一定更快。"** `C03` 是 conditional：设备/码率/分辨率/驱动四条件；多路并发时可能反而不如软解（§4.2）。
- **"硬解省电 10%。"** 泛化数字被源文档原文否定（"不能泛化为固定 10%"⚠️，§4.2）。
- **"buffer 用完不还也没事。"** 有限池耗尽 = 解码器等待/停摆（§4.1 + L06 实验 task 4）。
- **"回退就是从头再播。"** §8.4 八步是无感过渡：锁存 PTS_fail → 冻结 → 渐隐 → 销毁 → 软解 → seek → 追赶 → 恢复（§4.3）。
- **"flush 随手调。"** 绕过状态机保护顺序，在途 buffer 所有权链断裂 + 黑屏/爆音风险（§4.4 推导，待核验）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**buffer 是有限池，借还必须成对——release(true) 移交显示、release(false) 丢帧归还（`V27`，§4.1）→ 硬解省电来自 VPU 专用电路，但优势有四个条件限定，"固定省 X%"被源文档原文否定（`C03` conditional，§4.2）→ 硬解的脆弱面（实例有限/非标码流）决定了必须设计回退：八步状态机按顺序保护画面与音频（`V28`，§4.3）→ flush/销毁必须走状态机顺序，不能由渲染线程随手发起（推导，§4.4）→ 回退不是失败，是"无感降级"的设计目标（§6）。**

再自问三个"为什么"：为什么 buffer 池是"有限"的？为什么功耗优势要带四个条件？为什么回退状态机的顺序不能换？
