# 坐标变换与 MVP

> **本章回答**：同一个三角形，为什么经过几次矩阵乘法就能有透视、有远近，还能正确落到屏幕像素上？
> **写作纪律**：正文重组源文档的推导关键步骤，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：pilot 路线第 5 课·收官（L01 → L02 → L06 → L11 → L13），建议 55 分钟，含动手实验。
> **学习目标**（完成本章后你应能）：① 解释每个坐标空间存在的理由 ② 推导 MVP 的组合顺序 ③ 处理 NDC/Y-flip 的跨 API 差异——前置概念见 [L08 一帧怎么画出来](L08-一帧怎么画出来.md)。

## 1. 从一个问题开始

一个真实的事故场景（源文档 §4.2 记载的跨 API 事故）：一个在 OpenGL demo 里渲染正常的立方体，把着色器和矩阵**原样**搬进 Vulkan——画面近处被裁掉一半、深度全错。代码一行没改错，错的是两边对"深度范围"的默认约定不同（OpenGL 的 NDC z ∈ [-1,1]，Vulkan 是 [0,1]）。

另一个更隐蔽的：矩阵顺序写反。模型矩阵内部把 `T·R·S` 写反，物体会绕**世界原点**而不是自身原点旋转（源文档 §2.2 的专属症状）；而把整条链写成 `M·V·P`，投影被套在**原始局部坐标**上，w 分量从第一步就错了——画面整体畸变，不存在"看似能跑"。矩阵乘法不可交换，每一处顺序都有唯一的正确答案。

本章把这两个坑连根讲清：**每个坐标空间为什么必须存在（`V17`）、MVP 的组合顺序怎么推导（`V18`）、透视除法为什么不能手动做（`V19`）、跨 API 的 NDC 差异怎么处理（`V20`）。** 这四条断言目前都是 open/low（2026-11-19 B10 裁决确认登记），正文以主文档锚点为权威依据。

## 2. 学习前提

- **L08**：GPU 管线——顶点着色器输出 `gl_Position` 之后发生了什么（光栅化之前的固定管线阶段）。
- **L06**：FBO 与纹理坐标——本章 §4.4 会回收一个 L06 的伏笔（`getTransformMatrix`）。
- 数学：会算矩阵乘法 `A·B`；知道向量有 3 个分量。不需要学过图形学。
- 四个首次出现的术语，先给一句话解释：
  - **齐次坐标**：用 4 个分量 (x, y, z, w) 表示 3D 点——多出来的 w 让"除法"能表达透视，也让平移能写进矩阵。
  - **NDC**（Normalized Device Coordinates，归一化设备坐标）：透视除法之后、落到像素之前的标准化坐标，范围由 API 约定（如 [-1,1]）。
  - **视口**（Viewport）：NDC 到屏幕像素的映射规则。
  - **列主序 / 行主序**：矩阵在内存里的存放顺序——GLSL/GLM 列主序，HLSL 默认行主序，搞反了矩阵就是转置。

## 3. 直观认识

给一个物体**拍照**：先把它摆进房间（模型→世界），再架好相机（世界→观察），再决定用广角还是长焦（观察→裁剪），最后投影到相片（裁剪→屏幕）。每一步对应一个坐标空间与一个矩阵。

> **类比的边界**：拍照类比帮记住"五个步骤、各司其职"，但它不涵盖最关键的一步——真实的"投影"不是光学成像，而是**把远处的点按深度压进一个标准化盒子（NDC）**，靠的是齐次坐标的 w 分量；"广角/长焦"对应的是投影矩阵里 `1/tan(FOV/2)` 这个缩放系数，不是镜头物理。类比到"选镜头"为止，w 的工作它管不了。

## 4. 一步一步理解原理

### 4.1 六个空间：每个存在的理由

六个空间的职责分解（断言 `V17`，源表见[3D 变换 §1.1](../../../07-3D渲染与算法实现/3D变换与坐标空间.md#1-坐标空间链)）：

| 空间 | 单位/原点 | 由谁定义 | 典型用途 | 缺了它会怎样 |
|---|---|---|---|---|
| 模型空间（Local） | 美术导出 | 建模软件 | 顶点原始坐标 | 没法复用美术资产——每个模型都绑死在世界里 |
| 世界空间（World） | 场景统一单位 | 引擎 | 摆放、光照、剔除 | 没法摆放物体、算光照、做剔除 |
| 观察空间（View/Eye） | 相机在原点，看向 -Z（右手系） | 视图矩阵 V | 相机相对位置、高光 | 没有"相机"这个概念，镜头语言无从谈起 |
| 裁剪空间（Clip） | 齐次坐标，`-w ≤ x,y,z ≤ w`（GL） | 投影矩阵 P | 裁剪、透视除法前 | 视锥外的点没法高效裁掉，透视没有安放处 |
| NDC | `[-1,1]` 或 `[0,1]` | 透视除法 + API 约定 | 屏幕映射输入 | 跨 API 没有统一约定，每家硬件一套坐标 |
| 屏幕/窗口空间 | 像素 | 视口变换 | 光栅化 | 不落像素 |

```
local --Model--> world --View--> eye --Projection--> clip --perspective divide--> NDC --Viewport--> window
                                              （断言 V17：每步解决一个独立职责）
```

顶点着色器的最小职责就是前三步（源文档 §1.2 原文）：

```glsl
vec4 world = u_model * vec4(a_pos, 1.0);
vec4 eye   = u_view * world;
gl_Position = u_projection * eye;
```

传给片元的世界坐标/法线要**单独输出**，不能在片元里用 `gl_FragCoord` 反推；透视正确插值由硬件完成——插值的是 `attr / w`，片元里再乘回 `w` ✅（这就是 §4.3 "透视除法不能手动做"的插值面原因）。

### 4.2 MVP 的组合顺序：推导而不是背诵

**为什么是 `P·V·M`？** 列向量约定下，矩阵作用在向量的**右侧**——想先施加 M 再施加 V 再施加 P，写出来就是从右往左依次乘（断言 `V18`，源文档 §1.2/§2.1）：

$$
\text{gl\_Position} = P \cdot V \cdot M \cdot \begin{bmatrix} x \\ y \\ z \\ 1 \end{bmatrix}
$$

这与"先投影"的直觉正好相反：直觉里"先决定怎么拍"，但数学上投影矩阵必须**最后**作用——它输出的 clip 坐标需要的世界/观察信息已经在前两步里算完了（MVP 术语卡见站点术语表，绑定 `tools/glossary.json` MVP 词条）。

**分行推导**（教学算例：`v_model = (1, 1, 1)`；`M` = 沿 z 平移 -5；`V` = 相机在原点看向 -Z（本例取单位阵）；`P` = §4.3 的 60° 透视矩阵，aspect 16:9）：

| 步骤 | 运算 | 结果 | 语义 |
|---|---|---|---|
| ① 模型 → 世界 | `M·v` | (1, 1, −4) | 物体被摆进场景（平移 −5 后 z = 1−5 = −4） |
| ② 世界 → 观察 | `V·v1` | (1, 1, −4) | 相机在原点时观察坐标 = 世界坐标 |
| ③ 观察 → 裁剪 | `P·v2` | x=0.974·1, w=4 | f/aspect≈0.974 作用于 x；**w_clip = −z_eye = 4** |
| ④ 裁剪 → NDC | ÷w | x_ndc ≈ **0.244** | 透视除法由 GPU 固定管线完成（`V19`） |

x_ndc = 0.974/4 ≈ 0.244——与 §4.3 算例同口径（z_eye 越远 NDC 越靠中心）。每一步的"语义"列就是坐标空间存在的理由（§4.1 表）。

组合里的模型矩阵自己往往也是复合的：`M = T · R · S`——先缩放、再旋转、再平移（源文档 §2.2）。顺序写反的症状很具体：**物体会绕世界原点而不是自身原点旋转**。

主序陷阱（源文档 §2.1 的实践规则）：

| 概念 | 约定 |
|---|---|
| GLSL / GLM | 列主序 + 列向量，`M * v`，`A * B` 表示**先 B 后 A** |
| HLSL | 默认行主序 + 行向量，`mul(v, M)`，`mul(A, B)` 表示**先 A 后 B** |
| Vulkan / Metal | 与语言约定无关，只认你上传的字节 |

用 GLM 时直接 `glUniformMatrix4fv(..., GL_FALSE, &m[0][0])`，不要手动转置；从 HLSL/Unity 抄矩阵到 GLSL 出现"上下颠倒"，**先确认是主序问题还是乘法顺序问题**，不要盲目 `transpose`。（法线矩阵是唯一需要显式求逆的常用矩阵，机制见[源文档 §7](../../../07-3D渲染与算法实现/3D变换与坐标空间.md)，本章不展开。）

### 4.3 投影矩阵：把深度写进 w

透视投影的关键动作是**把深度信息写进 w 分量**。OpenGL 右手系（NDC z ∈ [-1,1]）的投影矩阵（源文档 §4.1，重组）：

$$
P =
\begin{bmatrix}
\frac{f}{aspect} & 0 & 0 & 0 \\
0 & f & 0 & 0 \\
0 & 0 & \frac{F+N}{N-F} & \frac{2FN}{N-F} \\
0 & 0 & -1 & 0
\end{bmatrix},
\qquad f = \frac{1}{\tan(fovY/2)}
$$

最后一行的 `-1` 就是全部透视魔法的来源：`w_clip = -z_eye`——越远的点 w 越大。用两个端点验证（源文档原表）：

| `z_eye` | `w_clip` | `z_ndc`（除以 w 后） |
|---|---|---|
| `-N`（近平面） | `N` | `-1` |
| `-F`（远平面） | `F` | `+1` |

**数值算例**（由上式推导，教学算例）：fovY = 60°、aspect = 16:9 → f = 1/tan(30°) ≈ 1.732，f/aspect ≈ 0.974。取同一个顶点 `x_eye = 1`：

| `z_eye` | `w_clip = -z_eye` | `x_ndc = 0.974·x_eye / w_clip` |
|---|---|---|
| `-2`（近） | 2 | ≈ **0.49** |
| `-10`（远） | 10 | ≈ **0.10** |

同一个 x_eye，离相机越远在 NDC 里越靠中心——**近大远小不是绘制技巧，是除以 w 的算术结果**（断言 `V19`：透视除法必须在 clip→NDC 由 GPU 固定管线完成）。把 FOV 从 60° 加大到 100°，f 从 1.732 降到 ≈0.839，同一顶点的 NDC 坐标进一步向中心收缩——视野收纳了更多场景（感知效果的解释见实验 selfTest：远处透视收敛更强，边线在画面边缘显得被拉长）。

**为什么透视除法不能手动做？**（实验 selfTest 原文口径）顶点着色器输出的是裁剪空间坐标，w 承载深度信息；透视除法由 GPU 固定管线在齐次裁剪之后统一完成。手动在顶点着色器里除掉 w，会破坏**透视正确插值**——硬件按 `attr / w` 插值、片元里乘回 `w`，提前除掉 w 之后插值变成屏幕空间线性，斜面上的纹理会扭曲，视锥裁切也失去了依据。

### 4.4 跨 API 差异：NDC 与 Y-flip

NDC 的默认约定**按 API 记表**（断言 `V20`，完整表见[源文档 §5](../../../07-3D渲染与算法实现/3D变换与坐标空间.md#5-ndc-与视口跨-api-差异表)）：

| API | NDC x/y | NDC z | NDC Y 方向 | 帧缓冲原点 | 正面绕序（默认） |
|---|---|---|---|---|---|
| OpenGL / GLES | `[-1,1]` | `[-1,1]` | 向上 | 左下 | CCW |
| Vulkan | `[-1,1]` | `[0,1]` | **向下** | 左上 | `VkFrontFace` 指定（常配 CW） |
| D3D 11/12 | `[-1,1]` | `[0,1]` | 向上 | 左上 | CW |
| Metal | `[-1,1]` | `[0,1]` | 向上 | 左上 | CW |
| WebGPU | `[-1,1]` | `[0,1]` | 向上 | 左上 | CCW |

两个最容易翻车的地方：

1. **深度范围不能靠视口救**。把 GL 矩阵直接交给 Vulkan，画面"近处被裁掉一半/深度全错"（负深度被裁掉）。Vulkan 的 `[0,1]` 版本只需改投影矩阵第三行（源文档 §4.2 给出完整矩阵并 ✅ 验证端点 `z_eye=-N → 0`、`-F → 1`）；**负视口高度只能翻转 Y，不能把 [-1,1] 变成 [0,1]**——深度范围必须在投影矩阵里改。
2. **Y 不要翻两次**。视口变换公式（源文档 §5.1）在 Vulkan 的 Y 向下约定下自然得到"从左上角量"的坐标，配合 NDC Y 向下最终方向正确——**不要在 shader 里再翻一次 Y**，否则二次翻转。

纹理 UV 原点是同一族问题（源文档 §5.2/§5.3）：OpenGL 纹理原点在左下、PNG/Android Bitmap 在左上、FBO 回读得到倒置图；统一策略是**在资源导入层决定一次约定，shader 里不做条件分支**。这里回收 L06 的伏笔：视频纹理（`GL_TEXTURE_EXTERNAL_OES`）的 UV 变换矩阵由 `SurfaceTexture.getTransformMatrix()` 给出，**不要自己假设原点**——L06 §4.1 的那条变换矩阵，在坐标语言里就是"把解码器的 UV 约定对齐到你的采样约定"。

视锥剔除（本章术语之一）也长在同一张矩阵上：对 `M = P·V` 提取六个平面（行组合 `r3 ± r0/r1/r2`，源文档 §6.1），配合包围球做**保守剔除**——平面未归一化会让剔除的尺度判断失效；对跨近平面的大物体直接丢弃则会出现"贴脸消失"（源文档 §6.2 分列两条）。

## 5. 数学原理 / 数据形态

把两个 API 的透视投影矩阵并排，差异全部集中在第三行：

$$
P_{GL}=
\begin{bmatrix}
\frac{f}{aspect} & 0 & 0 & 0 \\
0 & f & 0 & 0 \\
0 & 0 & \frac{F+N}{N-F} & \frac{2FN}{N-F} \\
0 & 0 & -1 & 0
\end{bmatrix}
\qquad
P_{[0,1]}=
\begin{bmatrix}
\frac{f}{aspect} & 0 & 0 & 0 \\
0 & f & 0 & 0 \\
0 & 0 & \frac{F}{N-F} & \frac{FN}{N-F} \\
0 & 0 & -1 & 0
\end{bmatrix}
$$

正交投影（源文档 §4.3）：`w = 1`，深度**线性**、不存在透视除法的精度挤压——2D/UI、平行光阴影贴图常用；改变相机距离只改变它是否被近/远裁剪面切掉，**不改变投影大小**（实验 selfTest 原文口径）。深度精度的完整推导在[光栅化深度与移动 GPU 架构 §2](../../../03-图形与GPU工程/光栅化深度与移动GPU架构.md#2-深度缓冲)（本章不展开）。

## 6. 工程应用与常见错误

**排查现场**（由源文档 §4.2/§4.4 重组的教学案例）：GL → Vulkan 移植后"近处被裁、深度全错"。按本章机制倒推：先查 NDC z 约定（§4.4 表）→ 确认是 [-1,1] 矩阵进了 [0,1] 管线 → 改投影矩阵第三行（不是加负视口高度）。若现象是"画面上下颠倒"，查下表第 3 行：NDC Y 方向与视口 Y 方向不一致；若是"透视畸变异常"，查 aspect 用了像素比而非宽高比、或 FOV 角度当弧度。源文档 §4.4 的五行"现象→原因"表值得整个抄进团队的移植 checklist：

| 现象 | 常见原因 |
|---|---|
| 物体被近平面裁掉 | `near` 过大；或用了 `[0,1]` 矩阵却按 GL 传 |
| 远处深度糊成一片 | `far/near` 比值过大（如 0.1 / 10000） |
| 画面上下颠倒 | NDC Y 方向与视口 Y 方向不一致（§4.4） |
| 透视畸变异常 | `aspect` 用像素比而非宽高比；FOV 角度当弧度 |
| 正交相机看不到物体 | 正交的 `N/F` 写成透视的符号 |

常见误区：

- **"MVP 只有一个矩阵。"** 它是三次变换的组合，且模型矩阵内部往往还是 T·R·S 复合（§4.2）。
- **"透视除法在顶点着色器手动做。"** 错——必须在 clip→NDC 由固定管线完成（`V19`）；手动除破坏透视正确插值（§4.3）。
- **"OpenGL 和 Vulkan 的 NDC 一样。"** 深度范围与 Y 方向默认都不同（`V20`）；负视口高度只翻 Y、`frontFace` 只改绕序，深度范围必须改矩阵。
- **"上下颠倒就 transpose 一下。"** 先分清主序问题还是乘法顺序问题（§4.2 的表）——盲目 transpose 只是掩盖症状，错误根源（主序或顺序）还在。
- **"包围球剔除越激进越好。"** 平面未归一化会让剔除的尺度判断失效（物体错误消失）；对跨近平面的大物体直接丢弃才会"贴脸消失"——正确做法是保留并与近平面求交，或交给 GPU 裁剪（源文档 §6.2）。

## 7. 动手实验

打开 [坐标变换与 MVP 实验](#/lab/transform-mvp)（定义在 `tools/labs.json`，离线可运行）。四个任务，每个对应本章一个机制：

1. **把 FOV 从 50° 调到 100°，观察远处边线的透视拉伸**——对应 §4.3 的 `f = 1/tan(FOV/2)` 缩放系数。
2. **切换透视/正交投影，观察深度感如何变化**——对应 §5 正交的 `w = 1`、深度线性。
3. **旋转模型 Y 轴，观察 M 矩阵和屏幕投影同时变化**——对应 §4.2 的组合顺序与 `M = T·R·S`。
4. **放大模型或拉近相机，观察顶点越过视锥后被裁切**——对应裁剪空间 `-w ≤ x,y,z ≤ w` 的裁剪依据。

做完用实验内置 selfTest 自查：透视除法为什么不能手动做、FOV 拉伸的系数解释、正交投影为什么不随距离缩放。实验边界（labs.json note 原文）：这个实验不依赖 Three.js 或 WebGL——投影矩阵和线框绘制都在本地 Canvas 2D 中完成，便于看清每一步数学含义。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**六个空间各管一件事（`V17`）→ 矩阵作用在列向量右侧，所以组合顺序是 P·V·M、模型内部 T·R·S（`V18`）→ 透视投影把深度写进 w（w_clip = -z_eye），近大远小是除以 w 的算术结果，且除法必须由固定管线完成否则破坏插值（`V19`）→ NDC 默认约定按 API 记表，GL→Vulkan 移植必须改投影矩阵第三行（`V20`）→ 所有"上下颠倒/深度全错/贴脸消失"都能从这张表和矩阵倒推出原因。**

再自问三个"为什么"：为什么投影矩阵必须最后作用？为什么 w 能承载"近大远小"？为什么负视口高度救不了深度范围？
