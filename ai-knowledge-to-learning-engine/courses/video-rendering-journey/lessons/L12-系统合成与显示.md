# 系统合成与显示

> **本章回答**：应用 present 之后，画面为什么仍可能延迟或撕裂？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：主课程 U4 第 2 课（prerequisites：L08），建议 35 分钟。本章无绑定实验（`tools/labs.json` 无 L12 实验），动手形式为图层路由决策练习 + 真机对比观察（§7）。

## 1. 从一个问题开始

L08 已经打破过一个直觉：`eglSwapBuffers` 只是**提交**后台缓冲，不等于画面已上屏（断言 `V34`）。这一章把"提交之后"的路走完。先看两个真实场景：

1. 车机中控播视频，解码器明明按时吐帧，画面却总比声音"慢半拍"——延迟不在解码，在哪？
2. 仪表指针快速扫过表盘，边缘出现**撕裂**——上半截是旧一帧、下半截是新一帧。应用明明画完了整帧，为什么屏幕上会拼出两帧？

两个问题的答案都在应用之外：**你的 buffer 还要经过系统合成器排队、选路、等扫描节拍，才变成屏幕上的光**（[GPU 基础 §3](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#3-一帧的端到端链路)）。这段路不归你的渲染代码管，但它的每一段都贡献延迟与功耗——不懂它，优化就会停在"GPU 明明很快"的困惑里。

## 2. 学习前提

- **L08**：Swap→View 树混合→SurfaceFlinger 链路初印象与 CPU/GPU 异步——本章把最后一环展开。
- **L06**：SurfaceTexture 与 BufferQueue"一体两面"——生产者写帧、消费者读帧的传输机制（[解码链路 §6.1](../../../02-解码与播放链路/解码与播放链路.md#61-surface-体系四组件-已验证)）。
- **L02**：V-Sync 与主时钟——显示节拍不是应用说了算。
- 术语先给一句话解释（SurfaceFlinger / DPU / HWC / VSync / Swapchain / 双缓冲 / 三缓冲在 `tools/glossary.json` 有权威术语卡）：
  - **SurfaceFlinger**：Android 的系统合成器——把多个应用/窗口的图层合成一帧显示输出（其他平台对应 QNX Screen、Weston 等）。
  - **HWC / DPU**：Hardware Composer / Display Processing Unit——显示硬件里的合成与扫描输出单元，能把若干图层**不经过 GPU** 直接叠到屏幕上。
  - **Swapchain**（交换链）：前后台缓冲的交换链——L08 讲过，`eglSwapBuffers` 调换的正是它。
  - **Overlay**（硬件覆盖层）：HWC/DPU 提供的硬件平面——一个图层占一个平面，直接扫描输出。
  - **BufferQueue**：生产者-消费者缓冲队列——Buffer 插槽在"空闲/已入队/被持有"三态间轮转（解码链路 §6.1）。
  - **frame pacing**（帧节奏）：按显示节拍**准时**提交，而不是尽快提交。

## 3. 直观认识

把显示链路想成**快递系统**：应用是发货仓（渲染出 buffer），系统合成器是**分拣中心**（收多个仓的货，决定怎么拼成一车），HWC overlay 是**直达专线**（整件货不拆包直接上车），GPU 合成是**重新打包线**（几件货拆了混装成一箱，费工费时），显示控制器是**按固定班次发车的司机**（VSync 节拍，到点才走）。

你的货（buffer）再快，也要等分拣、等班车——这就是"present 之后仍有延迟"的直觉来源。

> **类比的边界**：分拣中心不改动直达件的内容——overlay 路径上像素不被重画；但"重新打包"（GPU 合成）是真的逐像素重算，不是简单搬运。类比也覆盖不了**相位**问题：撕裂不是货错了，而是司机装货装到一半就发车（§4.2）。

## 4. 一步一步理解原理

### 4.1 系统合成器与 HWC/DPU 的职责（objective ①）

一帧的端到端链路，应用只负责前半段（[GPU 基础 §3.1 链路图](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#31-通用链路图)的 ASCII 重组）：

```
应用/引擎 → 剔除/排序 → RenderGraph → CommandBuffer → API/驱动
  → GPU（顶点→光栅→片元→混合）→ Swapchain/应用 Buffer
  → 系统合成器（SurfaceFlinger / QNX Screen / Weston）
      ├─ Overlay 可用 → HWC/DPU 硬件平面 ─┐
      └─ 需特效合成 → GPU 合成 ───────────┤
                                          → 显示控制器 → 屏/HUD
```

合成器之后的三个阶段，职责与瓶颈各不相同（[GPU 基础 §3.2 表](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#32-各阶段职责与瓶颈)后三行，断言 `V43`）：

| 阶段 | 输入 → 输出 | 常见瓶颈 | 对应优化 |
|---|---|---|---|
| 提交/呈现 | Buffer → 合成器 | fence 等待、队列拥塞 | 控制 in-flight 帧数 |
| 系统合成 | 多图层 → 显示帧 | **Overlay 平面不足、GPU 回退** | 对齐 HWC 格式/尺寸 |
| 扫描输出 | 显示帧 → 光子 | vsync 相位、面板响应 | frame pacing、低延迟模式 |

关键机制：**HWC/DPU 的硬件平面数量有限**。图层都能走 overlay 时，合成几乎不花 GPU；一旦平面不够或图层格式/尺寸不满足硬件要求，合成器就**回退 GPU 合成**——把多个图层当纹理重画一遍，功耗与延迟立刻上来（§3.2"Overlay 平面不足、GPU 回退"原文）。所以"对齐 HWC 格式/尺寸"不是玄学优化，是让图层留在直达专线上。

### 4.2 双缓冲/三缓冲与延迟的取舍（objective ②）

先回答撕裂：屏幕扫描输出是逐行进行的；如果扫描到一半时 buffer 被换成了新帧，上半截旧、下半截新——撕裂（机制为教学展开，源 §3.3 只给结论句；应用侧视角见 L08 `V34`"双缓冲调换避免撕裂"）。**双缓冲 + VSync** 解决它：只在垂直同步节拍切换缓冲（[GPU 基础 §3.3](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#33-双缓冲三缓冲与-frame-pacing)，断言 `V44`）。

三缓冲不是"更多更好"，而是一笔明确的交易（源 §3.3 原文口径）：

- **收益**：吸收 CPU/GPU **偶发超时**——某帧算慢了，还有一帧存货可显示，帧节奏更稳。
- **代价**：多一帧排队延迟 ⚠️。

**checkpoint ② 的答案：三缓冲不一定比双缓冲好。** 要稳节奏（容忍偶发慢帧）选三缓冲；要低延迟（车载仪表的指针/警示灯可信度）双缓冲更合适——源文档特别点名 frame pacing 对车载仪表的重要性。还有一条容易混的区分（源 §3.3 原文）：**Jank ≠ pacing 抖动**——长帧是某帧算太慢，pacing 抖动是帧完成时间不均匀；**三缓冲治后者，不治前者**。帧本身算得慢，加缓冲只是把慢帧藏进队列，延迟反而更大。

frame pacing 的定义值得单独记：不是"尽快提交"，而是"**按显示节奏准时提交**"。

### 4.3 什么图层适合硬件 overlay（objective ③）

路由判据一句话：**需要特效才走 GPU；纯显示优先 Overlay**（[GPU 基础 §3.4](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#34-视频相机参与时的分支)原文，断言 `V45`）。视频/相机帧的三条分支：

```
相机/VPU 帧 → dmabuf / AHardwareBuffer
   ├─ 直接送 HWC Overlay → 屏（最低延迟，无特效）
   ├─ EGLImage / VkImage → GPU 纹理 → 特效链 → 合成
   └─ NPU 输入 → 感知结果 → 可视化层 → GPU 渲染
```

**checkpoint ① 的答案**：Video/Camera/HUD 优先走硬件平面，因为它们是"纯显示"图层——通常无需复杂变换与像素级特效；overlay 路径**链路最短、延迟最低、且不需要 GPU 重画像素（功耗极佳）**。Android 组件层的对应物是 SurfaceView vs TextureView（[解码链路 §6.2 对比表](../../../02-解码与播放链路/解码与播放链路.md#62-surfaceview-vs-textureview-底层对比-已验证) ✅）：

| 维度 | SurfaceView | TextureView |
|---|---|---|
| 合成机制 | SurfaceFlinger 作为独立 Hardware Overlay 硬件合成 | View 树绘制阶段当普通纹理 GPU 合成 |
| 驱动线程 | 独立后台渲染线程，不抢 UI 主时间片 | 主 UI 线程 RenderThread，受布局重绘/动画影响 |
| 物理延迟 | 极低（直写物理窗口双缓冲） | 较高（通常 1~3 帧 View 树二次合成及管线同步延迟） |
| 交互能力 | 极差（难支持倾斜/遮罩/半透明/滚动混排） | 极强（矩阵变换/动画/剪裁/Alpha 过渡） |
| 功耗 | 极佳（overlay 无需 GPU 重画） | 一般（纹理采样 + 二次混合） |

（源表另有"线程安全"行——SurfaceView 极高 / TextureView 偏低，此处聚焦延迟/功耗/交互，完整六行见源 §6.2。）

选择原则（源 §6.2 原文）：极致低延迟低功耗的纯播放 → SurfaceView；需要 UI 变换、动画叠加、滚动容器嵌入 → TextureView。TextureView 的合成成本正是断言 `C01`（**conditional**：通常更灵活但可能更耗合成成本）。

**数字纪律**（源 [§6.3](../../../02-解码与播放链路/解码与播放链路.md#63-直出与纹理化播放-已验证) ⚠️ 原文）：任何"固定延迟区间""全程零拷贝"都必须加设备与系统版本条件；SurfaceView 直出延迟**通常**低于 TextureView，但具体数值受设备合成策略、缓冲区数量、系统版本影响；**"TextureView 一定慢很多"是绝对化错误表述**。上表的"1~3 帧"是源给的经验区间，不是保证值。

### 4.4 延伸：智驾数据怎么进画面

智驾可视化不是"把摄像头画面投到屏上"，而是把感知/规划结果**重新画成可理解的图形**（[GPU 基础 §3.5](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#35-智驾数据如何进入画面)）：传感器 → ADAS SoC 推理 → BEV/目标轨迹 → 消息总线 → 座舱 SoC → 可视化引擎 GPU 绘制 → 合成器 → 仪表/中控/HUD。源文档的安全警示值得原样记住：**安全警示（AEB 提示、接管请求）应有不依赖复杂 3D 管线的兜底路径**——合成与显示链路的可靠性在这里是安全问题，不只是体验问题。

## 5. 数学原理 / 数据形态

本章没有新公式，核心数据形态是 **BufferQueue 的三态轮转**（[解码链路 §6.1](../../../02-解码与播放链路/解码与播放链路.md#61-surface-体系四组件-已验证) ✅）：

```
Buffer 插槽状态：空闲 → 已入队（生产者写满提交）→ 被持有（消费者取走）→ 空闲
双缓冲：2 个插槽轮转；三缓冲：3 个插槽——多出的 1 个就是"存货"，
也是 §4.2 那"多一帧排队延迟"的物理来源（教学示意，机制对应源 §3.3）。
```

延迟的账要**分段算**：渲染耗时（L07/L08 的带宽与提交账）+ 排队等待（in-flight 帧数 × 帧间隔）+ 合成路径（overlay ≈ 0 额外 GPU 开销 vs GPU 回退的重画成本）+ 扫描相位（最多等一个 VSync 周期）。源文档给的是各段瓶颈与优化方向（§3.2 表），**不给固定总延迟数字**——任何"端到端 X ms"的说法都要带设备与版本条件（§6.3 ⚠️ 纪律）。

## 6. 工程应用与常见错误

**排查现场**（由 GPU 基础 §3.2 与解码链路 §6.2 重组的教学案例）：车机视频层用 TextureView 实现，UI 一跑动画视频就顿，且延迟偏高。按 §4.3 机制倒推：TextureView 走 View 树 GPU 合成，与 UI 动画抢同一个 RenderThread 和 GPU → 两个症状同源。该图层是纯播放、无变换需求 → 改 SurfaceView 走 overlay，延迟与功耗同时下降。反过来，若产品要求视频圆角 + 淡入淡出，overlay 做不了——这时 TextureView 的额外成本是**买交互能力的钱**，不是 bug。

常见误区：

- **"present 了就是显示了。"** 后面还有合成器选路 + 扫描节拍（`V34`/`V43`，§4.1）。
- **"三缓冲一定更流畅更好。"** 它治 pacing 抖动不治长帧，代价是一帧排队延迟；仪表类低延迟场景双缓冲更合适（`V44`，§4.2）。
- **"撕裂是 GPU 画错了。"** 是扫描与换缓冲的相位问题，双缓冲 + VSync 解决（§4.2）。
- **"所有图层都走 GPU 合成最灵活。"** overlay 平面有限，纯显示图层挤占 GPU 合成是功耗与延迟双输（`V45`，§4.1/§4.3）。
- **"TextureView 一定慢很多 / 直出延迟固定 X ms。"** 绝对化错误；数值带设备与版本条件（源 §6.3 ⚠️，`C01`）。

## 7. 动手核查清单

本章无绑定实验；动手形式为**决策练习 + 真机对比观察**：

- [ ] **图层路由决策**（做什么：给"全屏视频 / 圆角视频卡片 / 仪表指针 / 相机预览 / 带滤镜的相机预览"五个图层逐一判 overlay 还是 GPU → 预期：纯显示无变换的走 overlay，需特效/变换的走 GPU → 对应机制：§4.3 判据）。
- [ ] **真机对比 SurfaceView/TextureView**（做什么：同一视频源两种组件各播一段，观察 UI 动画时的流畅度差异 → 预期：TextureView 受 UI 重绘影响更明显 → 对应机制：§4.3 驱动线程行；差异幅度带设备条件）。
- [ ] **数一数 overlay 平面**（做什么：叠加多个视频/相机图层直到画面合成路径变化 → 预期：超过硬件平面数后出现 GPU 回退迹象（功耗/帧时间变化）→ 对应机制：§4.1 平面不足）。
- [ ] **区分长帧与 pacing 抖动**（做什么：用系统 trace 工具（Systrace，见[跨平台 §2.3](../../../04-跨平台与高性能架构/跨平台与高性能架构.md#23-量化评估维度)）抓帧时间序列 → 预期：能指出"某帧特别长"与"帧完成时间不均匀"是两种形态 → 对应机制：§4.2 Jank ≠ pacing 抖动）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**present 只是提交（`V34`）→ 系统合成器收多图层，选 overlay 直达或 GPU 重打包，平面有限会回退（`V43`）→ 扫描按 VSync 节拍，双缓冲 + VSync 治撕裂，三缓冲吸收偶发超时但多一帧延迟，治 pacing 抖动不治长帧（`V44`）→ 纯显示图层（Video/Camera/HUD）优先 overlay：链路短、延迟低、功耗佳；要特效才走 GPU，SurfaceView/TextureView 是组件层对应物（`V45`/`C01`）→ 一切延迟数字带设备与版本条件。**

再自问三个"为什么"：为什么 overlay 平面不足会同时伤延迟和功耗？为什么三缓冲治不了长帧？为什么安全警示要有独立于 3D 管线的兜底路径？
