# 从文件到码流

> **本章回答**：MP4 和 H.264 是什么关系？MediaCodec 为什么不负责 demux？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：主课程 U2 第 1 课（prerequisites：L01/L02），建议 35 分钟。本章无绑定实验（`tools/labs.json` 无 L04 实验），动手形式为容器字段走读核查（§7）。

## 1. 从一个问题开始

一个新手必踩的崩溃：拿到一个 `.mp4` 文件，把**整个文件**的字节直接灌进 `MediaCodec`（Android 的系统级硬编/硬解 API，正式定义见 §4.3）配置的输入缓冲——解码器立刻抛出异常。这不是偶发 bug：源文档 ✅ 段写明，**封装流直接灌入解码器，解码器因无法识别容器格式，会在第一步熵解码（entropy decoding——码流压缩语法的第一步，把压缩位流还原成语法元素）阶段产生非法指令异常**（断言 `V26`，[音视频基础理论 §3.1](../../../01-基础理论/音视频基础理论.md#3-编码与封装容器)）。

为什么？因为 MP4 和 H.264 根本是两种东西：**MP4 是容器**（负责组织轨道与时间索引），**H.264 是码流**（负责压缩语法）。把带集装箱外壳的货直接塞进拆包机，拆包机第一步就会被集装箱外壳卡死。本章把这个职责边界讲透——它是 L05 硬解 ownership、L06 纹理化整条链路的地基。

## 2. 学习前提

- **L01**：三层数据模型——压缩层/原始层/显示层（[音视频基础理论 §1](../../../01-基础理论/音视频基础理论.md#1-媒体处理三层数据模型)）。本章的容器与码流都属于**压缩层**。
- **L02**：PTS/DTS——容器里的时间索引正是它们在文件侧的家。
- 四个首次出现的术语，先给一句话解释：
  - **容器（Container）**：把多路压缩码流打包成一个文件、并记录时间索引的封装格式（MP4/MKV/FLV）。
  - **码流（Bitstream）**：编码器输出的压缩数据本体（H.264/H.265/AAC）。
  - **Demux（解封装）**：把容器拆开、分离出各路压缩码流的步骤——**不做任何解压缩**。
  - **NALU**：H.264/H.265 码流的基本传输单元（Network Abstraction Layer Unit），控制元数据与图像数据都以它为单位组织。

## 3. 直观认识

把播放一条视频想象成**工厂拆包流水线**：容器是带清单的集装箱（哪条轨道在第几格、时间怎么排），码流是集装箱里压得紧紧的货物，解码器是拆包机——它只认**裸货物**，连集装箱外壳都不认识。

源文档把流水线的一句话结论放在最前面（✅，断言 `V26` 的管线部分）：**解封装（Demux） → 解码（Decode） → 渲染（Render）**，各模块物理与逻辑上严格隔离，职责混淆是"事故"而不仅是"不优雅"。

> **类比的边界**：拆包流水线类比不覆盖"时间"——容器不但分装轨道，还记录每个帧的时间索引（L02 的 PTS/DTS 就住在容器的索引表里）；也不覆盖"错误恢复"——真实现场里解封装还有容错与重同步职责（L13 之后的专题）。类比到"先拆箱再上机"为止。

## 4. 一步一步理解原理

### 4.1 三段管线的职责表：谁负责什么、谁明确不负责

三段管线的职责表（[解码与播放链路 §1.2](../../../02-解码与播放链路/解码与播放链路.md#1-音视频核心管线与职责边界-已验证)，✅；断言 `V26`）：

| 模块 | 物理职责 | 技术边界（明确不负责） | 工业级组件 |
|---|---|---|---|
| **解封装（Demux）** | 解析容器格式（MP4/FLV/MKV），分离出压缩的音视频码流 | **不参与任何解压缩计算** | `FFmpeg (libavformat)`、`MediaExtractor` |
| **解码（Decode）** | 将压缩码流还原为原始像素（YUV/RGB）或 PCM | **不感知容器封装格式**，不处理多轨同步 | `MediaCodec`（硬解）、`FFmpeg (libavcodec)`（软解） |
| **渲染（Render）** | 原始数据投射到屏幕像素 / 驱动声卡 | 不具备解压与格式纠错能力 | `SurfaceFlinger`/`OpenGL`、`AudioTrack` |

表的第三列和第二列同样重要：**"不负责"是写进架构的边界，不是实现细节**。这正是 §1 开箱崩溃的机制——解码器被设计为"不感知容器格式"，你喂它容器字节，它只能按码流语法去熵解码，第一步就遇到非法语法。

还有一个易错点（[主文档 §1.7](../../../02-解码与播放链路/解码与播放链路.md#1-音视频核心管线与职责边界-已验证)）：**播放器 ≠ 解码器**——播放器是架构容器，解码器只是其中一个环节。

### 4.2 容器与码流：两种职责、两张表（objective ①）

容器与码流的职责分工（断言 `V26`，[音视频基础理论 §3.1](../../../01-基础理论/音视频基础理论.md#3-编码与封装容器)，两段均 ✅）：

**容器**——核心职责是**组织轨道和时间信息**，不执行压缩：

| 容器格式 | 核心特征 | 典型应用 |
|---------|---------|---------|
| MP4 (ISOBMFF) | Box 层次结构，索引完备，支持流式 | 点播、下载播放 |
| MKV (Matroska) | 开源，支持几乎所有编码格式 | 高清影片存档 |
| FLV | 简单轻量，支持流式写入 | 早期直播推流 |
| fMP4 | 分片结构，支持增量写入 | HLS/DASH 流媒体分发 |
| WebM | 基于 MKV，VP8/VP9/Opus | Web 平台视频 |

**码流**——核心职责是**执行压缩语法**（熵编码、帧间预测、变换量化）：

| 码流类型 | 压缩标准 | 典型用途 |
|---------|---------|---------|
| H.264 (AVC) | 最广泛兼容的视频编码 | 通用视频、直播、会议 |
| H.265 (HEVC) | 比 H.264 节省约 40% 码率 | 4K/8K 高清视频 |
| AAC | 主流音频编码 | 通用音频、流媒体 |
| Opus | 低延迟、高质量 | 实时通信（WebRTC） |

所以"MP4 和 H.264 的关系"的准确表述是：MP4 是**装**着 H.264 码流的容器——同一个 MP4 也可以装 H.265；同一段 H.264 码流也可以被装进 TS 或 MKV。**容器与码流的组合是正交的**。

### 4.3 MediaExtractor 与 MediaCodec：谁拆箱、谁拆货（objective ②）

MediaCodec 的定位（断言 `V01`，✅，[解码与播放链路 §1.4](../../../02-解码与播放链路/解码与播放链路.md#1-音视频核心管线与职责边界-已验证)）：它是 Android **系统级底层硬编/硬解 API，仅负责编解码计算，无任何解封装能力**，必须搭配 `MediaExtractor` 或 `FFmpeg` 解封装后才能使用。

工业级标准组合三步（[主文档 §1.6](../../../02-解码与播放链路/解码与播放链路.md#1-音视频核心管线与职责边界-已验证)，✅）：

1. **FFmpeg 全格式解封装**，分离压缩码流；
2. **MediaCodec 硬解优先**（送 VPU）；
3. **硬解失败自动切换 FFmpeg 软解兜底**（Fallback 状态机机制见主文档 §8.4）。

为什么是"FFmpeg 解封装"而不是 MediaExtractor？FFmpeg 的模块化分工（[主文档 §1.5](../../../02-解码与播放链路/解码与播放链路.md#1-音视频核心管线与职责边界-已验证)，✅）：

| 子库 | 职责 |
| ----------- | -------------- |
| libavformat | 解封装 / 封装 |
| libavcodec | 软解码 / 软编码 |
| libavfilter | 音视频滤镜 |
| libswscale | 图像格式转换 |

`libavformat` 是"全格式拆包工"——负责对各类非标或常规流媒体进行高兼容解封装（源文档 §1.3：「全格式拆包工」为原话）；MediaExtractor 是 Android 平台内置解封装器（§1.2 表中与 libavformat 并列的解封装组件）。选型的权衡（非标码流鲁棒性对比见主文档 §2.3 表）属于 L05 的硬解话题，本章记住边界即可。

### 4.4 NALU、SPS、PPS：码流内部的"说明书"（objective ③）

H.264/H.265 码流由一系列 **NALU** 构成，物理上划分为控制元数据与残差图像切片（断言 `V11`，[音视频基础理论 §3.2](../../../01-基础理论/音视频基础理论.md#3-编码与封装容器)，✅）。三个关键控制单元：

- **SPS**（Sequence Parameter Set，序列参数集）：全局控制信息——Profile/Level、帧率、最大参考帧数、分辨率与裁剪区域、色度降采样格式（4:2:0/4:4:4 等）。✅
- **PPS**（Picture Parameter Set，图像参数集）：图像级编码参数——熵编码模式（CAVLC/CABAC）、初始 QP、Slice 组划分。✅
- **SEI**（Supplemental Enhancement Information）：非解码必需的元数据——高精度时间戳、场景切换指示、用户自定义数据（弹幕、传感器遥测）。✅

**缺 SPS 的后果**（源文档 ✅ 原文口径）：解码器无法获知分辨率、色度格式和参考帧队列长度，无法为 I 帧分配正确的解码缓冲区（DPB），所有后续帧都成为无意义的二进制数据——黑屏或解码崩溃。这就是为什么"喂码流之前必须先送参数集"不是可选步骤。

### 4.5 Annex B 与 AVCC：同一批 NALU 的两种分界方式

NALU 在文件里怎么分界？两种格式（断言 `V25`，[音视频基础理论 §3.2](../../../01-基础理论/音视频基础理论.md#3-编码与封装容器)，两表 ✅）：

| 特性 | **Annex B** | **AVCC** |
|------|------|------|
| 分隔方式 | 起始码前缀 `0x00000001` / `0x000001` | 4 字节大端序长度前缀 |
| 容错性 | 强——解码器可在任意位置检索起始码重连同步 | 弱——长度字段损坏后续全部错位 |
| 随机访问 | 需全局扫描起始码，效率较低 | 消除全局扫描开销，效率极高 |
| 适用场景 | 流媒体传输、网络广播、裸码流 | 本地存储、快速随机定位 |
| 典型协议/容器 | RTP / RTSP / TS 流 | MP4 / MKV |

**两者不可混用**。而 Android MediaCodec 的实际行为比流传的"必须 Annex B"更宽容（源文档 ⚠️有条件成立，原表述已修正）：通过 `CSD-0`/`CSD-1` 把 SPS/PPS 作为 codec-specific data 配置后，**可直接喂入 AVCC（length-prefixed）NALU**，无需转 Annex B——这是 MP4 点播/直播的常用路径；仅当目标是裸流硬解或个别只认 Annex B 的底层驱动时，才需转换（在 NALU 前插入起始码）。条件成立的边界：取决于解码器实现与 CSD 配置方式。

## 5. 数学原理 / 数据形态

MP4 的容器结构是可数的（源文档 §3.3，✅）：ISOBMFF 的 **Box 树**——每个 Box 前 4 字节是长度、后 4 字节是类型：

```
[ftyp]──文件类型声明（最前端）
   │
[moov]──元数据+索引（播放索引的"大本营"）
   │     └─ trak ── mdia ── minf ── stbl ──┬─ stco/co64（数据块绝对偏移）
   │                                       ├─ stsc（每 Chunk 的采样数）
   │                                       ├─ stsz（每帧精确字节大小）
   │                                       ├─ stts（采样时长 → 帧号↔PTS 转换）
   │                                       └─ stss（关键帧 I 帧序列号）
[mdat]──音视频二进制有效载荷
```

**帧寻址流程**（源文档 ✅ 原文）：输入目标 PTS → stts 计算帧序号 → stss 检索最近 I 帧 → stsc + stco 计算物理文件偏移 → 从 mdat 提取数据送解码器。这正是 L02"精准 seek 先定位关键帧"在**文件侧**的实现机制——avformat_seek_file 的落点由这张索引表决定。moov 前置（Fast-Start）与流式播放的关系见[源文档 §3.3](../../../01-基础理论/音视频基础理论.md#3-编码与封装容器)。

## 6. 工程应用与常见错误

**排查现场**（由源文档 §3.1/§3.2 ✅ 段重组的教学案例）：新同事把"黑屏或解码崩溃"的锅甩给硬解驱动。按本章边界倒推：先查**喂进 MediaCodec 的是什么**——若是封装流直灌，熵解码第一步即异常（`V26`）；若是码流但没先配 SPS/PPS（CSD），解码器无法建 DPB，同样黑屏（§4.4）；若 CSD 配了、码流是 AVCC 而解码路径只认 Annex B，需按 §4.5 的条件判断是否转换。三步全部对上边界表（§4.1），才轮得到怀疑驱动。

常见误区：

- **"MediaCodec 也能做 demux。"** 错。它仅负责编解码计算，必须搭配 MediaExtractor/FFmpeg（`V01`）。
- **"MP4 就是 H.264。"** 容器与码流正交：MP4 可装 H.264/H.265，同一 H.264 码流可进 TS/MKV（§4.2）。
- **"播放器就是解码器。"** 播放器是架构容器，解码器只是其中一环（主文档 §1.7）。
- **"MediaCodec 只认 Annex B。"** 不准确——配好 CSD 后可直接喂 AVCC；是否需要转 Annex B 取决于解码器实现（⚠️有条件成立，§4.5）。
- **"Annex B 和 AVCC 只是格式偏好。"** 分界机制不同（起始码 vs 长度前缀），容错与随机访问特性相反，混用直接错位（`V25`）。

## 7. 动手核查清单

本章无绑定实验（`tools/labs.json` 无 L04 实验）；动手形式为**容器字段走读核查**——拿一个真实 MP4 文件，用任意容器检查工具（ffprobe 等）或 Android `MediaExtractor.getTrackFormat()` 逐项确认（做什么 → 预期看到什么 → 对应机制）：

- [ ] **文件里实际有几条轨道？** 预期：视频/音频各一条（多音轨影片更多）——对应 §4.2 容器"组织轨道"。
- [ ] **视频轨道的码流类型与容器？** 预期：码流为 H.264/H.265、容器为 MP4——对应 §4.2 两张表与正交关系。
- [ ] **能否找到 SPS/PPS？** 预期：MP4 中以 CSD-0/CSD-1 形式随轨道格式出现——对应 §4.4 参数集与 §4.5 CSD。
- [ ] **NALU 分界是起始码还是长度前缀？** 预期：MP4 中为长度前缀（AVCC）——对应 §4.5 两种格式。
- [ ] **stss 表（关键帧号）在哪里？** 预期：拖拽进度条只在 stss 列出的帧间落点——对应 §5 帧寻址流程。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**封装流直灌解码器会在熵解码第一步异常（`V26`）→ 所以三段管线 Demux→Decode→Render 职责严格分离，各自的"不负责"写进边界（§4.1）→ 容器管轨道与时间索引、码流管压缩语法（`V26`），两者组合正交（教材推导，§4.2）→ MediaCodec 无解封装能力，工业组合是 FFmpeg 解封装 + 硬解优先 + 软解兜底（`V01`，§4.3）→ 码流内部以 NALU 组织，SPS/PPS 是解码器建 DPB 的前提，缺了黑屏（`V11`，§4.4）→ NALU 分界两格式：Annex B 起始码（容错强/随机访问弱）vs AVCC 长度前缀（相反），CSD 配好后 MediaCodec 可直喂 AVCC（`V25`，§4.5）→ MP4 的 moov 索引表是 L02 精准 seek 在文件侧的落点（§5）。**

再自问三个"为什么"：为什么解码器要被设计成"不感知容器"？为什么 SPS 缺失会导致整段码流无效？为什么 TS 流偏爱 Annex B 而 MP4 偏爱 AVCC？
