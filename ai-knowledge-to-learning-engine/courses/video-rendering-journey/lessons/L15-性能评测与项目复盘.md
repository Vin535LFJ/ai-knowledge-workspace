# 性能评测与项目复盘

> **本章回答**：没有设备矩阵和测试条件，性能数字能写进结论吗？
> **写作纪律**：正文用自己的语言展开机制，权威定义与完整细节链接主文档锚点；陌生术语首次出现给出一句话解释。
> **路线位置**：主课程 U6 第 1 课（prerequisites：L12、L14），建议 45 分钟。本章无绑定实验，动手形式为评测方案设计 + 结论审计（§7）。

## 1. 从一个问题开始

两份优化报告摆在面前：

- 报告 A："合批优化后 **CPU 占用下降 98%**，性能显著提升。"
- 报告 B："主线程 CPU 活跃周期从 **12.0 ± 2.1 ms/帧降至 0.24 ± 0.05 ms/帧**（Snapdragon 8 Gen 2 / Adreno 740 / Driver 5xx.x，n=1000，测试码流 SHA-256:…，VMAF 93.1→92.4）。"

数字上 A 更震撼，工程上 B 才可用。A 缺了什么？——设备型号、驱动版本、样本量、测量口径（"CPU 占用"是全局负载还是目标线程？）、测试输入、画质代价，一样都没有（[项目实战 §5.4](../../../05-项目实战/项目实战指南.md#54-结果表达规范) 的示例口径）。**没有证据链的性能数字不是结论，是广告。** 这一章给你证据链的完整模板。

## 2. 学习前提

- **L07/L08**：带宽账与帧循环——你知道该测什么（帧时间、提交成本、带宽）。
- **L12**：frame pacing 与 Jank——长帧和节奏抖动是两种病，评测要分开看。
- **L14**：分层地图——优化可能"降质换速度"，所以画质必须一起测。
- 术语先给一句话解释（VMAF / 带宽 / DrawCall / Frame in flight 在 `tools/glossary.json` 有权威术语卡）：
  - **PSNR**（峰值信噪比）：像素级误差（MSE）的对数表达，越高越接近参考图。
  - **SSIM**（结构相似性）：从亮度/对比度/结构三个维度比较图像，比 PSNR 更接近人眼感知。
  - **P99 帧时间**：99% 的帧都快于这个值——它盯着最坏的那 1%，平均值盯着"整体感觉"。
  - **Systrace / perfetto**：Android 内核级追踪工具——记录 CPU 调度、线程状态与图形管线事件（perfetto 是 Systrace 后继）。

## 3. 直观认识

性能评测像**体检报告**：单次测量不代表健康（要多次采样），仪器要校准（设备基准统一），空腹/餐后要注明（测试条件），而且不能只看"平均指标正常"——最坏的那项指标（P99）才决定风险。

> **类比的边界**：体检参考范围是人群通用的；性能基准**没有通用参考范围**——同一 SoC 不同驱动版本可差 20–30%（源 §5.1），所以"帧时间 16 ms 算好"这种话必须带设备与条件。类比也覆盖不了画质维度：体检没有"降质换速度"问题，渲染优化有——所以性能数据必须与画质数据成对出现（§4.3）。

## 4. 一步一步理解原理

### 4.1 严谨实验三原则（objective ①）

[项目实战 §5.1](../../../05-项目实战/项目实战指南.md#51-严谨实验三原则)（✅ 已验证，断言 `V51`）：

1. **硬件基准绝对统一**：所有数据标明 SoC 型号 + GPU 驱动版本（格式 `Snapdragon 8 Gen 2 / Adreno 740 / Driver 5xx.x`）；同一 SoC 不同驱动可差 **20–30%**（源给区间）；**严禁跨设备混合测试后取平均**。
2. **输入测试用例标准化**：对比方案用同一组用例，标明分辨率/帧数/编码规格（如 H.264 High Profile Level 4.0, 10Mbps, CABAC——基于上下文的自适应二进制算术编码，H.264 的熵编码方式）；严禁不同编码参数横向对比；推荐附测试码流 **SHA-256** 保证可复现。
3. **内核节点物理监控**：**严禁用应用层日志评测性能**——日志自身引入 I/O 延迟且时间戳精度不足。用内核级工具：

| 工具 | 用途 |
|---|---|
| Systrace | CPU 调度与线程状态追踪 |
| ADB Shell（top -H） | 实时进程级 CPU/内存监控 |
| dumpsys meminfo | 进程级内存详细分解 |
| perfetto | 现代化全系统追踪（Systrace 后继） |

### 4.2 P50/P99 与平均值：三种"帧时间"（objective ②）

先算一笔账（教学算例）：100 帧里 99 帧 10 ms、1 帧 100 ms——

$$
\text{平均} = \frac{99 \times 10 + 100}{100} = 10.9 \ \text{ms} \qquad P99 = 100 \ \text{ms}
$$

平均值说"一切正常"（10.9 ms < 16.7 ms 预算），P99 说"有一帧卡了 6 倍帧预算"（取最坏 1% 边界口径）。**平均值掩盖尖刺，P99 暴露尖刺**——而用户记住的恰恰是那一次卡顿。车机更应看 **P99 帧时间、最坏帧延迟、热稳定性、启动时间**，而不是峰值吞吐（断言 `V32`，[GPU 基础 §1.5](../../../03-图形与GPU工程/GPU与渲染引擎基础与链路.md#15-别只看-tops)）；智驾方案把"**用平均帧率代替 P99**"直接列为选型红旗信号（[智驾渲染方案 §7](../../../04-跨平台与高性能架构/智驾渲染方案.md#7-方案选型-checklist)）。P99 的测量用 Perfetto/Systrace/GPU trace（智驾方案 §5.1 预算表）。

CPU 侧同理有口径陷阱（源 §5.2 ✅）：测 CPU 占用必须测**目标线程的活跃周期**（主线程单帧内 running 状态时长，ms/帧，Systrace sched 标签），**不是全局 CPU 负载**——后者被系统后台进程污染，反映不了应用真实开销。报告 A 的"CPU 占用下降 98%"若测的是全局负载，数字本身就不成立。

### 4.3 画质指标：防止"降质换速度"（objective ③）

性能只有功耗/帧率/显存三维不够——**画质必须量化，否则"优化"可能只是"降质换速度"**（[项目实战 §5.3](../../../05-项目实战/项目实战指南.md#53-画质指标)，断言 `V53`）。

全参考指标（有原始参考图）：

| 指标 | 衡量什么 | 优点 | 局限 |
|---|---|---|---|
| PSNR | 像素级 MSE 的对数表达 | 计算极快、可解释 | 与人眼感知相关性弱，对模糊/锐化不敏感 |
| SSIM | 亮度/对比度/结构相似度 | 比 PSNR 更接近感知 | 对严重失真、位移敏感 |
| MS-SSIM | 多尺度 SSIM | 兼顾粗细结构 | 计算量更大 |
| VMAF | 机器学习融合多特征 | 与主观评分相关性高 | 需参考视频，模型有版本差异 |

$$
\mathrm{PSNR} = 10 \log_{10}\left(\frac{MAX^2}{\mathrm{MSE}}\right)
$$

- **符号含义**：MAX 是像素最大值（8bit 图像 = 255），MSE 是均方误差。
- **数值算例**（教学算例）：MSE = 100 → PSNR = 10·log₁₀(65025/100) ≈ **28.1 dB**；MSE 减半 → PSNR +10·log₁₀2 ≈ **+3.0 dB**；MSE 降至 1/4 → +6.0 dB。
- **工程后果**：**PSNR 高 ≠ 好看**——整体偏暗/偏色可能仍有高 PSNR，轻微锐化可能降 PSNR 却更讨喜（源原文）。所以锐化/降噪后不能只比 PSNR。
- **源文档勘误（已闭合）**：源 §5.3 原句"PSNR 每提高 6 dB，MSE 约减半"为数学笔误——按公式 10·log₁₀2 ≈ 3.01 dB，**+3 dB≈MSE 减半、+6 dB 对应降至约 1/4**。**2026-11-23 经用户批准源文档已更正（D21）**，本课表述与源一致（历史审读记录见 G2-L15 材料，不改写）。

无参考指标（无原图）：NIQE/BRISQUE（自然场景统计）、块效应/振铃检测、**主观 MOS（真人打分，最终仲裁）**。比较编码方案用**码率-质量曲线**：固定编码器/preset（速度-质量预设）/GOP（图像组，帧间预测结构）/分辨率，比曲线下面积或同码率质量，报告 BD-rate（同质量码率节省），不比单点。

评测陷阱五行（源 §5.3 表）：参考图未对齐→指标严重偏低；色彩范围/传输函数不一致→偏色被误判为算法问题；tone mapping（HDR→显示范围压缩，L14 §2 已讲）前算指标→HDR 截断失真；只测单帧→掩盖时域闪烁/拖影；锐化后直接比 PSNR→误杀观感提升。

**工程口径**（源原文）：**性能数据与画质数据必须成对出现**——"帧时间从 16.2 ms 降到 11.4 ms，VMAF 从 93.1 降到 92.4"，而不是只报帧率提升。

### 4.4 结果表达规范：结论的格式（checkpoint ②）

[项目实战 §5.4](../../../05-项目实战/项目实战指南.md#54-结果表达规范)（✅，断言 `V52`）：

- **置信区间与标准差**：所有量化结果报均值 ± 标准差或 95% CI，格式 `帧时间 = 16.2 ± 1.3 ms (95% CI: [15.8, 16.6], n=1000)`；最少连续 **1000 帧**（约 16.7 s @60FPS）；严禁单次值或最佳值。
- **标注约束条件**：有条件结论必须写明约束（如 `conditionally true 约束于 Android API ≥ 26`）；常见维度：OS 版本/驱动版本/硬件特性/运行时状态。
- **严禁模糊口径**：❌"发热大幅度降低""性能显著提升" → ✅"SoC 温度从 62.3 ± 1.1°C 降至 54.7 ± 0.9°C（降幅 12.2%，n=1000）"。

**checkpoint ② 的答案**：趋势比绝对数字可靠，是因为绝对数字绑定具体设备/驱动/输入/运行时状态——换一个条件就可能翻转（驱动差异 20–30%）；而"同条件下 A 方案比 B 方案少一次拷贝"这类**机制性趋势**跨条件稳定。[学习路径指南](../../../00-导航与索引/学习路径指南.md)的工程红线原文：任何"提升 X% / 降低 Y%"的结论，**没有设备型号、样本量与测试条件，只能写成趋势，不能写成保证**。

## 5. 数学原理 / 数据形态

一份可用结论的完整证据链（模板，各要素出处见 §4）：

```
结论：主线程 CPU 活跃周期 12.0 ± 2.1 → 0.24 ± 0.05 ms/帧
设备：SoC 型号 + GPU 型号 + 驱动版本          ← 原则 1
输入：分辨率/帧数/编码规格 + 码流 SHA-256      ← 原则 2
测量：Systrace sched 线程 running 时长，n=1000 ← 原则 3 + §5.4
画质：VMAF 93.1 → 92.4（成对出现）            ← §5.3
约束：API Level / 运行时状态                  ← §5.4
```

评测方案设计 = **设备矩阵 × 标准用例 × 指标集（帧时间 P50/P99 + 线程活跃周期 + 显存物理页 + 温度 + 画质）× 条件标注**。显存注意区分"已分配"与"实际映射物理页"（源 §5.2 ⚠️：前者可能含未提交虚拟地址空间）；功耗测瞬时电流而非平均功耗（源 §5.2 ⚠️ 待验证口径，工具 Monsoon 硬件采样）。

## 6. 工程应用与常见错误

**排查现场**（由源 §5.4 示例与 §5.2 口径重组的教学案例）：审计报告 A 的"CPU 占用下降 98%"。逐项追问：测的全局负载还是线程活跃周期？（§4.2——若是全局负载，数字不成立）哪颗 SoC 哪个驱动？（缺）样本量？（缺）码流规格？（缺）画质代价？（缺）。补全后重写为报告 B 的格式——同一个优化，从"广告"变成"可复现的工程结论"。复盘的价值正在于此：**结论可以被别人按证据链重跑验证**。

常见误区：

- **"平均帧率达标就没问题。"** 平均值掩盖尖刺；车机看 P99/最坏帧/热稳定性（`V32`，§4.2）。
- **"CPU 占用下降就是优化生效。"** 全局负载被后台污染；测目标线程活跃周期（§4.2）。
- **"PSNR 涨了就是画质好了。"** 感知相关性弱；结合 SSIM/VMAF 与主观 MOS（`V53`，§4.3）。
- **"帧率提升就是成功。"** 可能是降质换速度；性能与画质数据成对出现（§4.3）。
- **"单次跑分可以写进报告。"** 严禁；n≥1000 + 均值±标准差/CI（`V52`，§4.4）。
- **"提升 X% 放之四海皆准。"** 没有设备/样本/条件只能写趋势不能写保证（§4.4）。

本章无绑定实验；动手形式为**方案设计 + 结论审计**：

- [ ] **手算 PSNR**（做什么：MSE=100、8bit → 预期：≈28.1 dB；再算 MSE=50（≈31.1 dB，+3 dB 减半）与 MSE=25（≈34.1 dB，+6 dB 降至 1/4）→ 对应机制：§4.3 公式与勘误）。

## 8. 总结与主动回忆

合上文档，复述这条因果链（说不出来就回到对应小节）：

**性能数字要成为结论必须有证据链：设备基准统一（驱动差 20–30%）+ 输入标准化（SHA-256）+ 内核级监控（禁应用层日志）（`V51`）→ 平均值掩盖尖刺，车机看 P99/最坏帧；CPU 测线程活跃周期不测全局负载（`V32`/`V52`）→ 画质必须量化且与性能成对：PSNR 快但感知弱，SSIM/VMAF 更接近人眼，MOS 最终仲裁（`V53`）→ 表达规范：n≥1000、均值±标准差/CI、约束标注、禁模糊口径；无条件数字只能写趋势（`V52`）。**

再自问三个"为什么"：为什么严禁跨设备混合取平均？为什么锐化可能降 PSNR 却值得做？为什么"只测单帧"是评测陷阱？
