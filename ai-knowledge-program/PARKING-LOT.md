# PARKING LOT · 暂时不做的一切

> 规则：新想法**默认不进入当前执行计划**，先登记到这里。
> 登记 ≠ 立项；解冻需要真实需求验证 + 用户明确批准。冻结 ≠ 删除，已有成果全部保留。
> **本文件不是待办任务列表**：这里只放"现在不做"的想法，当前任务一律在 NOW.md。

## 准入规则（每个新想法先过这四问，由 Program Manager 分类）

- A. 是否直接**阻碍**当前主项目目标？是 → 可考虑进入当前任务计划（NOW.md）。
- B. 是否是完成当前阶段**不可缺少**的能力？是 → 作为 Engine 内部能力实现，不急于独立抽取。
- C. 是否可以在当前项目内部实现，而**不需要独立抽取**？是 → 留在项目内。
- D. 是否已在**多个项目**中验证了复用价值？是 → 才评估抽取为独立项目（走 PD 决策）。

硬规则：**不得自动创建新仓库、子项目或大型基础设施**。新增项目/子系统/工具/架构默认不进当前计划——除非是当前阶段目标不可缺少的条件，且经用户明确批准。未回复不视为同意。
Knowledge/Skills/MCP/Tools 同一原则：知识跟随领域和产品归档；通用 Skills 留在现有来源仓库；MCP/Tools 由使用项目维护；需要统一发现时**先考虑轻量索引或登记规范，不立即开发完整管理系统**。

### GitHub Project Radar（自动化情报）
- 价值：优秀项目发现、热点追踪、增长趋势、研究情报报告，作为 Engine 外部研究入口。
- 提出原因：人工收藏 GitHub 项目逐渐增多。
- 暂缓原因：Engine 消化能力未建成前，Radar 只会不断收藏却无法消化；现阶段人工收藏 + 简单清单 + web 搜索足够。
- 重新评估：项目追踪成为持续且明确的工作负担 + Engine P8 输入合同就绪。永不自动向知识库导入未经审核内容。资产详情见冻结表。

### Learning Experience Design（正式设计体系）
- 价值：教材阅读体验、交互表达、信息架构、学习路径、视觉系统、响应式、可访问性、页面质量审核的系统化。
- 提出原因：学习网站需要稳定体验质量。
- 暂缓原因：P1 期间只保证必要可用性与基础质量；设计体系必须从真实页面迭代中提炼，不能先验建设。
- 重新评估：P10 通过 + PD-003 四条件满足。产出永远是 Engine 内部 Skill，不独立成仓。资产详情见冻结表。

### 独立 Knowledge Repository（知识库收录项目）
- 价值：跨领域知识集中收录与统一管理。
- 提出原因：知识内容随多领域增长，担心分散。
- 暂缓原因：知识应跟随实际领域和产品归档；"收录→消化"闭环就是 Engine P8 输入合同 + source inbox，拆出去反而切断闭环（PD-003 §2.5）。
- 重新评估：多领域知识库互相引用出现真实混乱时，按 PD 流程重议。

### 独立 Skills Registry（skill 收录管理项目）
- 价值：跨项目统一发现、安装、配置 Skills。
- 提出原因：技能数量增长（供应库已 37 技能），多项目消费。
- 暂缓原因：供应库已有分类/安装/兼容性纪律；跨项目登记是 Governance 解冻后的 Registry 职责；现在立项 = 重复建设。
- 重新评估：多个项目真的需要统一发现/安装/配置时，**先做轻量索引或登记规范**，不建完整管理系统。

### MCP / Tools Registry
- 价值：统一登记和发现各项目使用的 MCP 与工具。
- 提出原因：工具随项目增多。
- 暂缓原因：当前由各使用项目内部维护即可，无真实跨项目发现痛点。
- 重新评估：同 Skills Registry——真实痛点出现后先轻量索引，不建管理平台。

### 统一 Agent 控制中心 / 通用多 Agent Orchestrator / 超级平台
- 价值：一站式管理所有知识、Skills、MCP、Tools、Agent 和项目。
- 提出原因：项目群要素增多，直觉上想要中央管理。
- 暂缓原因：**极易演变成比原始产品还复杂的新项目**；用户明确不需要（2026-11-19 任务书 §04）。Engine P9 只做项目内轻量状态机，不做通用 Orchestrator。
- 重新评估：不列入当前路线图；仅当多个真实项目反复验证同一管理痛点后重议。

### 大型项目管理 Dashboard / 新的通用文档管理平台
- 价值：可视化进度与文档集中管理。
- 提出原因：项目群管理需求增长。
- 暂缓原因：Program 四文件 + 各项目自有治理已覆盖当前需求；Dashboard/数据库/自动调度属于"为管理而管理"的复杂度（P0 明确不做）。
- 重新评估：仅当 Markdown 统筹层被证明无法承载真实管理负担时，先考虑轻量索引，不建平台。
